# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # Start development server (Express + Vite middleware) on port 3000
npm run build    # Vite production build to /dist
npm start        # Run production server (serves /dist statically)
```

```bash
npm run typecheck   # tsc --noEmit (run `npm ci` in packages/engine first for its vitest types)
npm test            # offline app checks: scripts/test-dossier-cards.ts, test-dossier-pipeline.ts (end-to-end with Gemini faked at fetch), test-dossier-cache-hit.ts (published cards served without re-rating, Supabase faked in memory), test-rating-command.ts (the Rate command serves the same cards without routing), test-player-search.ts (Rate suggestions), test-chat-dossiers.ts (chat reading and showing cards), test-chat-consistency.ts (chat vs stored cards), test-live-football.ts (ESPN and FPL parsing, club reports and lookup statuses, feeds faked), test-evidence-ledger.ts, test-research-agent.ts (brief, two stages, reflect, model and tools faked), test-situation-snapshot.ts (first-choice XI, club snapshot store and build), test-figure-gate.ts (unsupported precise figures removed), test-history-research.ts (Wikipedia and ESPN past seasons read into evidence, lookups kept for good, era snapshots, settled debates, the debate brief and its card checks; sources and model faked), test-history-chat-pipeline.ts (a question about the past end to end), test-live-chat-pipeline.ts (a question about the present end to end), test-gaffa-name-matching.ts, test-club-managers.ts

cd packages/engine && npm ci && npm test   # outlook engine + manager-fidelity vitest suite
```

CI (`.github/workflows/ci.yml`) runs all of the above plus `npm run build` on every PR and push to `main`. The tests need no network or API keys; add new offline checks to `npm test`.

## Deploying

The live app (futbolpedia.ai.studio) is hosted by Google AI Studio and does not deploy from GitHub on its own. A change goes live in three steps, all of which are needed:

1. **Push to GitHub and merge into `main`.** The pull script copies `main` only, so a pushed branch or an open PR is not live.
2. **Run the pull script in Google AI Studio** (`sync.sh`: `degit` of `dukerwang/Futbolpedia` into the workspace, `npm install`, `npm run build`).
3. **Publish from Google AI Studio.** Until this step, the live app keeps serving the previously published build.

So when reporting that a fix is done, say whether it is merged, and remind the user that the AI Studio pull and publish are still needed before it reaches the live app.

## Environment Variables

- `GEMINI_API_KEY` — Google Gemini key. Vite injects it into the client as `process.env.API_KEY` (read by `services/aiClient.ts`); the server's `/gemini-api-proxy/*` also uses it.
- `API_FOOTBALL_KEY` — API-Football key (used by `server.ts`). The free plan can't read the current season or use `last`/`next`, so it only helps dossier grounding for past seasons and the manager cross-check; chat research uses the live routes below.
- `GAFFA_BASE_URL`, `FUTBOLPEDIA_READ_SECRET` — server-only Gaffa integration (see `.env.example`)

Supabase publishable keys are hardcoded (safe for client exposure): Futbolpedia's in `services/dossierCache.ts`, Gaffa's in `services/gaffaAuth.ts`. The Supabase JS client is loaded via a `<script>` tag in `index.html` and accessed at `window.supabase`, not via an npm package.

## Architecture

### Server (`server.ts`)
A single Express server handles everything:
- `/api/football/player`, `/api/football/squad`, `/api/football/fixtures` — API-Football lookups (hide `API_FOOTBALL_KEY`), with in-memory caches for player facts and team context. `apiFootballGet` logs every refused call (API-Football answers plan limits with HTTP 200 and an `errors` field).
- `/api/live/club`, `/api/live/player`, `/api/live/table` — current-season facts from two free, keyless, unofficial feeds (`services/liveFootball.ts`): ESPN's site API (a club's matches in all competitions with both XIs, formation slots and subs, fixtures, league tables) and the Fantasy Premier League feed (each Premier League player's starts, minutes and output, and the injury and suspension list). Cached on the server for every user; each lookup logs a `[live]` line. Anything a lookup couldn't get comes back in `missing` with a status: `empty`, `not_covered` (no free source has it, such as injury lists outside the Premier League) or `failed`. `/api/live/club` also returns the structured `report` the situation snapshot reads; the writer's `get_club_recent_team` tool strips it. There is deliberately no general pass-through route: the app is public, so one would let anyone spend the key
- `/api/history/club-season`, `/api/history/player` — facts about past seasons (`services/historyFootball.ts`): Wikipedia's article on a club's season (manager, league finish, cup runs, top scorers, every squad player's appearances and goals, the top of the league table) and on a player (season-by-season appearances and goals, caps by year, honours by club), plus ESPN's results in every competition and the starting XIs of eight league matches spread across the season, for seasons from 2003-04 on (`season` parameter). Past seasons don't change, so a club season is kept for good, in memory and on disk under `.cache/history/` (it survives a restart); a player's article is kept a week, since an active player's numbers move. Each lookup logs a `[history]` line. The season in progress is refused (`not_covered`): the live routes cover it
- `/api/gaffa/context`, `/api/gaffa/chat` — Gaffa integration behind `FUTBOLPEDIA_READ_SECRET`
- `/gemini-api-proxy/*` — forwards AI Studio's redirected Gemini calls with the server-side key
- In dev: Vite is mounted as Express middleware (`middlewareMode: true`); in prod: serves `/dist`

### AI pipeline (`services/`)
`geminiService.ts` is the entry point (`sendMessageToAI`) and a re-export barrel for older imports. Each turn:
1. **Route** — `turnRouter.ts` `classifyTurn` tries 0ms regex fast paths (archive, single dossier, compare, challenge, ranking, club tactics), then falls back to a schema-enforced Flash classifier. The result is a `TurnRoute` (`intent`, `analyticalMode`, target players/clubs, search queries).
2. **Single dossier** — checks the in-conversation dossier, the saved archive, the in-memory calibrated pool, and the shared Supabase cache (`dossierCache.ts`), in that order. `dossierStore.ts` is a barrel over the dossier modules: `dossierCards` (card keys, slugs, evaluation dates), `dossierCache` (Supabase cache, versioned archive, sharing, Global Dossier Hub), `dossierContext` (history serialization, references, locked/saved/prior-rating blocks), `dossierLedger` (grep tool, peer ledger) and `dossierPatch`. Shared cards are found under the typed name, the names on his other cards, and the names `getPlayerIdentity` gives him (`groundingService.ts`: one grounded Flash call returning the name football coverage commonly uses, his full name and his career status), so "zico" finds a card published as "Arthur Antunes Coimbra". A new card is always named by that known-as name (`cardName`), so one player never gets two cards. On a miss, `groundingService.ts` runs API-Football and Google Search grounding in parallel and `dossierSynthesizer.ts` generates the card with `responseSchema`. It then enforces calibration invariants deterministically and scrubs unverified manager mentions.

**Ratings are the model's judgment of footballing ability.** Overall is never computed from attributes. Tiers (`constants/ratingTiers.ts`, Scout's Code §II) describe how good a footballer a version is on one all-era standard; positional rank, honours and dominance of an era are evidence, never the band itself. While rating, the model fills `calibration.peerPlacement`: which `<calibrated_peer_ledger>` peers this version was better than, level with, or not as good as. `ratingPlacement.ts` resolves those names to ledger cards (same edition preferred, never the player himself, ambiguous names ignored) and moves the Overall into the range that placement allows (strictly above/below when integers leave room, a tie otherwise). A self-contradictory placement changes nothing. The resolved placement is stored on the card (`peerPlacement`), shown under the benchmark, and serialized for chat.
**Scout panel and @ mentions.** Ratings start in the Scout panel (`ScoutDesk.tsx`, opened by the header's Scout button or ⌘K), not in chat. You type or paste names, pick Current or Prime, and each name becomes a queued job that `App` runs two at a time through `ratePlayer` (`geminiService.ts`). `ratePlayer` builds the route with `routeForRating` (`ratingCommand.ts`) and runs the same `rateDossier` a typed rating reaches, with `ratingTask` as the message, so caching and editions behave identically. Finished cards land in your dossiers, and **Ask** puts one in the chat box as a mention. Typing `@` in chat lists cards only: your dossiers and the shared cards from `fetchCardIndex` (`dossierCache.ts`, a field-only select cached 10 minutes), ranked by `playerSearch.ts` (`PlayerPicker.tsx`). A mentioned card joins the conversation, and the model reads each mention as `cardReference`, so the edition carries over. Typed "rate X" still works as a chat turn.
3. **Everything else** — `conversationalScout.ts` handles live dossier challenges (structured patch → `applyDossierPatch`) and prose turns (comparisons, debates, rankings, tactics). A prose turn that needs live facts researches first (`researchAgent.ts`); a thread about primes, past seasons or a past decade goes through the debate brief instead (see Questions about the past below):
   - **At once, in parallel**: each spotted club's live data and stored snapshot; for a club with no fresh snapshot, its research pass (shared with the build that stores one); a web search on the question itself, unless every club already has today's snapshot; and the brief. A message that `looksLikePresentQuestion` starts that search in `sendMessageToAI` while the turn is still being routed (`startQuestionSearch`), so the classifier's couple of seconds aren't on the critical path; a wrong guess costs one search, never time. The players the router spotted get their season record at once, and a record naming a club the turn hasn't opened opens it, so the snapshot covers the club he actually plays for. The brief waits at most `STORED_PEEK_MS` for stored snapshots. A grounded web search takes about 9 s on Flash, so research runs inside a budget: nothing that has to wait for the brief can include a search and still finish near 12 s.
   - **Brief** (one Flash call, low thinking, about 5 s; medium took about 12 s): works out what the question needs, and for a question about the present puts change at the centre (`focus`: what is distinctive about this team or player this season and why). It outlines the answer and plans further lookups from typed tools (`researchTools.ts`), each tagged `facts` or `analysis`, and is told what's already running so it doesn't repeat it. The brief and reflect prompts carry `RESEARCH_COVERAGE_NOTE`, which says what no source covers and how to work around it, so the planner searches team news instead of asking again for an injury list that doesn't exist.
   - **The brief's lookups**: live feeds (`/api/live/*`: a club's results, last four competitive XIs with positions and, for Premier League clubs, season starts and the injury list; a Premier League player's season; a league table) and stored cards always run. A web search runs only if it can finish (`SEARCH_ESTIMATE_MS`) before `RESEARCH_DEADLINE_MS`; otherwise it's filed as not started. Analysis searches wait briefly for the feeds, then run with the live facts (`formatFactContext`) so the digest flags sources describing an earlier team. Every web digest dates its points by the source's publication date. At the deadline research stops waiting. A lookup still running is set aside: if it finishes while the snapshot is being built, the writer still gets it; otherwise it's filed as too slow. A club research pass still running finishes for its build.
   - **Club snapshots**: the clubs the router spotted, and the brief's club lookups, go through `clubSnapshots.ts` (see Shared club snapshots below). A fresh stored snapshot is read before the brief (up to `STORED_PEEK_MS`) so it plans around it.
   - **Situation alongside the brief, then reflect**: on a turn about the present, the situation snapshot starts as soon as its inputs are in (the club feeds, each club's stored snapshot or research pass, the spotted players' records), so it runs while the brief does rather than after research. Clubs the brief adds later get what code works out for them. A reflect call (low thinking; skipped when research ran to the deadline or past `REFLECT_CUTOFF_MS`) reads the lookup log (`formatLookupLog`: found, empty, not covered, failed), discards web entries from earlier seasons that the live facts contradict (`discardEntries`, web only), and may add one round of up to three quick lookups (a search only while the turn is well inside its budget). The situation snapshot (`situationSnapshot.ts`) turns the evidence into a dated picture of the present: code works out each club's first-choice XI from recent starts and season starts (recent matches weigh more, domestic cups half, injured players never picked, an even split named only when another player started there at least twice and as often), who's out and recent form; one low-thinking call adds what changed since last season, what's distinctive, players' current situations and what's still unknown. A stored snapshot's story replaces that call for its club; past `SITUATION_CUTOFF_MS` the snapshot is code only.
   - **Writer**: reads `<situation_snapshot>` first, then the evidence ledger (`evidenceLedger.ts`: numbered entries, gaps grouped by status, web entries tagged when every source predates the season) as `<factual_foundation>`, and the brief as `<research_brief>`, at low thinking since the planning is done. It argues from the snapshot and commits to one starter per role, naming an alternative only for an even split. It runs at low thinking on every prose turn (medium held the first token back by 15 s or more on card debates). It has `get_league_table` alongside the other live tools, and is told which cards the turn already looked for and didn't find, so it doesn't spend a tool round on them. It keeps its full tool set (`proseToolMode`), so it can look up what research missed; only turns answered from stored cards or the archive are limited to local tools. A follow-up in the same thread reuses the last snapshot. The chat prompt separates facts (only from the snapshot, ledger, tools or cards; say plainly when something can't be verified) from judgment (decisive), and counts precise figures (statistics, fees, percentages, table positions and points, minutes of events, shirt numbers, quotations) as facts. On a researched turn, `figureGate.ts` checks every precise figure in the reply against the turn's evidence (snapshot, ledger, cards, the writer's tool results, the conversation, and passages its own search grounded): a figure counts only when the same number sits beside the same kind of word. An unsupported figure takes its sentence with it (in a table, only its cell), on the stream and the final reply; removals log a `[FigureGate]` line. Each step logs a `[Perf]` line.

   The design and later phases are in `docs/superpowers/specs/2026-10-31-agentic-research-harness-design.md`; `docs/superpowers/evals/live-questions.md` is the question set, and `npm run eval:live` (`scripts/eval-live-questions.ts`) runs it through the pipeline in-process and has a grader model with Google Search and the live feeds score stale facts, invented facts, whether the answer says what changed, decisiveness and hedged roles. The grader is the same Flash model that writes the answers, so compare runs with each other rather than reading scores as absolute. Supabase isn't loaded outside the browser, so a plain run measures cold turns; `--warm` answers each question once first to measure turns that reuse snapshots. Reports go to `docs/superpowers/evals/reports/`.

**Questions about the past.** A thread about past seasons, primes, eras or all-time comparisons (`threadIsHistorical`) runs `runDebateResearch` (`debateBrief.ts`) instead of the live research:
   - **Debate brief** (one Flash call, medium thinking, temperature 0): what the question turns on (`criterion`: peak level, sustained level, output, influence, versatility, or mixed), two to four criteria that settle it, the versions compared (the windows on their cards, or club seasons), where the honest disagreement lies, the strongest counter-case, a committed verdict (or an order, for a ranking), and up to `DEBATE_CALL_LIMIT` lookups for only the facts the verdict depends on: `club_season` and `player_career` (the history routes), cards, and the odd web search. The prompt lists the cards in play in rating order with their peer placements.
   - **Card check** (`debateConsistency.ts`, code): when the question turns on how good the players were (peak level or mixed), a ranking's carded entries are put in card order (Overall, then peer placement, then the brief's order; uncarded entries keep their places) and a head-to-head verdict goes to the side whose card is above. Level cards leave it to the criteria. What moved is passed to the writer as `cardNotes`.
   - **Settled debates**: a new chat's checked brief is stored in `era_snapshots` under the question's words (filler dropped, order and case ignored, `debateSignature`) and the cards' fingerprint, so the same question, with the same cards, reuses its verdict and skips the brief call. A re-rated card changes the fingerprint and reopens it. Follow-ups in a thread always write a new brief.
   - **Records and era snapshots**: the lookups run in parallel, and a web search gets `SEARCH_BUDGET_MS` beyond the records before it's left out of the turn (a grounded search takes 9 to 13 s); each club season or player window looked up reads its stored era snapshot (see Shared era snapshots below) and starts a background build for up to `MAX_ERA_BUILDS` that nobody has built.
   - **Writer**: gets `<debate_brief>` (criteria in order, versions, disagreement, counter-case, the settled verdict or order, card notes, the cards' order) and argues criterion by criterion, answers the counter-case, and closes on the brief's verdict. It may state a precise figure only when `<factual_foundation>` or a card gives it, keeps every fact to its own season, and names a past coach only from the evidence. It reads cards with local tools and gets the full set only when a lookup failed. Web entries aren't tagged as predating the season, the manager gate and today's coach lookup are skipped (they'd rewrite a past coach as "the current setup"), and the figure gate runs, reading the evidence's tables by their columns (`expandTables`) and counting titles and trophies.
   - `docs/superpowers/evals/historical-questions.md` is the question set; `npm run eval:live -- --set historical` runs each question twice through the pipeline with the shared cards read from Supabase through a read-only client (`scripts/eval-history.ts`), and the grader scores blended seasons, myths, use of criteria, the counter-case and decisiveness, then compares the two runs, and each paraphrase pair, for the same verdict. Figures get their own check: one call lists every precise figure an answer states, and a second checks each with search (a one-pass grader passed them all). `--regrade <report.json>` reruns that check on saved answers.

**Chat stays on the stored cards.** A new dossier shows in chat as a one-line stub carrying `dossierKey`; `buildHistoryContents` swaps each stub for the full card, so the model sees cards where the user saw them. Challenge turns get the challenged card plus the full card of every other player in the thread (in the same edition), and the thread's earlier replies keep their closing verdicts. A follow-up with no timeframe in a prime debate stays on prime cards. After generation, `dossierNumberGate.ts` puts any misquoted attribute of a card in play back to its stored value; it never touches Overall/Potential, which debate prose may propose on purpose.

**Chat reads cards on its own.** "How good is <player>" is a question, not a rating: `playerQuestionSubject` routes it to chat as `player_qa`. For chat and compare turns, `sendMessageToAI` looks up each target player's card in your dossiers and the shared card index (`dossierLookup.ts`, which never rates anyone), so the model answers from it. A question about one player shows his card under the reply; a player nobody has rated gets a Scout offer that queues him in the Scout panel. The prose model also has `look_up_dossier` and `show_dossier` tools, and the turn returns what it showed or found missing through `onAttachments`. A message that only mentions cards, or only asks to see them ("let me see @…", `chatIntent.ts`), posts the cards without a model turn.

`aiClient.ts` wraps `@google/genai`: `generateStructured` (schema JSON), `runGroundedSearch`, and `generateProseTurn` (streaming chat with local tools `grep_saved_dossiers` / `grep_gaffa_market` and the live data tools `get_club_recent_team` / `get_player_season`). Per-task model, thinking level and temperature come from `constants/modelProfiles.ts`.

### Gaffa mode (`services/gaffaChatService.ts`)
Separate chat domain from dossier synthesis. When the ChatInput **Gaffa** toggle is on, `App` routes to `sendGaffaMessage` — prose only, never `responseSchema` dossiers. Rules come from curated `constants/gaffaRules.ts` (`GAFFA_RULES_SNAPSHOT`, versioned). Soft auto-detect in `services/gaffaDetect.ts` nudges switching mode when default chat looks Gaffa-specific; it does not silently inject Gaffa context.

**Club connect:** sign in through `services/gaffaAuth.ts` and pick a club (RLS context loader), paste league + club IDs in the connect strip, or open `#/gaffa/<leagueId>/<clubId>`. Express `GET /api/gaffa/context` proxies to Gaffa `GET /api/integrations/futbolpedia/context`. The live bag fills `GaffaContextBag` (roster, budget, standings, matchup, XI, listings, auctions, FA pool, league settings); `gaffaLineupAudit.ts` derives lineup audits, alerts and bid valuations from it.

### Shared club snapshots
`clubSnapshots.ts` keeps each club's situation (first-choice XI, absences, form, what changed since last season, what's distinctive this season) in the Supabase `club_snapshots` table, keyed by the club name the live data resolves to, like `club_managers`. A turn reads the stored row first; when it's missing, more than a day old or built under an older `SNAPSHOT_VERSION`, a build runs `researchClub` (three searches at once: changes since last season, a tactical analysis read against the live facts, and team news where no injury list covers the club) and `summarizeClub` (the situation call), then stores the snapshot for everyone. The research pass is shared with the turn that started it, which files its results as evidence instead of searching the same things. Builds start with the brief when the turn is likely about the present, are shared by concurrent requests, and a failed build is never stored (retried after 10 minutes). A turn uses a snapshot that's ready within `SNAPSHOT_GRACE_MS` of its first round; one still building finishes for the next turn. The XI, absences and form always come from today's live data; only the story is reused. Bump `SNAPSHOT_VERSION` when the snapshot's shape or build changes. Like `club_managers`, any client can write a row, and every user's writer reads it as facts; story text is length-capped client-side, but nothing on the server yet stops a bad write. A database trigger that stamps `built_at` server-side, checks the row's shape and refuses to replace a fresh row would narrow that, though the first write of a club's day would still come from a browser.

### Shared era snapshots
`eraSnapshots.ts` keeps permanent snapshots in the Supabase `era_snapshots` table (`supabase/migrations/20261101130000_era_snapshots.sql`): a club season (coach and usual XI, shape and style, record, what defined it, figures copied from the sources, and claims often misstated) and a player's window (role, clubs, coaches and teammates, honours and output, the same figures and misstatements). Each is keyed by the Wikipedia article its facts came from and the normalized season or window, so "Arsenal" and "Arsenal FC" share one. The first turn that looks one up starts `buildEraSnapshot` in the background: the record it already fetched, two searches read against it, and one medium-thinking call that writes only from that evidence. Later turns read it as an `era_snapshot` evidence entry. Concurrent requests share a build, and a failed build isn't stored (retried after 10 minutes). The table also holds settled debates (`kind = 'debate'`). Rows are kept for good: the `keep_era_snapshots` trigger skips any update that doesn't carry a newer `version`, and there's no delete policy. Like `club_snapshots`, any client can insert a row for a key nobody has built yet; bumping `ERA_SNAPSHOT_VERSION` rebuilds every row.

### Manager fidelity
API-Football and model memory both lag coaching changes, so neither decides who manages a club. `services/clubManagers.ts` looks it up live: a focused Google-grounded Flash search per club (coach, appointment date, immediate predecessor, source), cross-checked against API-Football's `pickCurrentCoach` record (the search wins a disagreement; no search answer means nobody is named). Results are shared through the Supabase `club_managers` table and refreshed at most once a day per club. Nothing is maintained by hand.
- **Cards:** the dossier prompt forbids manager names in card prose. After synthesis, `attachVerifiedManager` sets `profile.clubManager` (shown on its own "Manager:" line of current cards, with its verified date) and scrubs the prose in strict mode, so only the verified coach can be named, and nobody when the lookup found no one. API-Football's registered club decides whose coach that is; the card's club stands in only when API-Football has no record, and when the two disagree (`isSameClub`) nobody is named.
- **Chat:** `conversationalScout` looks up the clubs in play, passes them to the model as `<verified_managers>`, and gives them to the scrub as `clubManagers`. A turn about the past skips both: it names past coaches only from its evidence.
- **Gates** (`packages/engine/src/gates/managerMentions.ts`): `scrubUnverifiedManagerText` replaces coach names the turn didn't verify. `scrubFormerCoaches` rewrites a club's immediate predecessor to its current coach, only for clubs the text names and never for someone currently coaching another club in play. `strictCurrentCoach` closes the loophole where a sacked coach counts as verified because search text mentions him.
- API-Football's coach is no longer written into grounding text. It's kept only as the lookup's cross-check.

**Critical quirks:**
- `gemini-3.8-flash` rejects `ThinkingLevel.MINIMAL` (HTTP 400); `aiClient.ts` maps the `minimal` tier to `LOW`.
- `SIMULATION_YEAR` / `SIMULATION_SEASON` (`prompts/scoutCore.ts`) are computed once at module load from the real date via `getRealWorldFootballSeason`, so the system instruction stays byte-stable within a process for Gemini's implicit prompt caching. Per-turn prompts read the date through `getCurrentSeasonInfo()`.
- The EAFC playstyle directory is only injected when the query matches an EAFC pattern — `buildConversationalScoutInstruction(includeEAFC)` controls this.
- `CALIBRATION_EPOCH_MS` in `dossierCache.ts` marks the last rating recalibration. `isRatedOnCurrentScale` keeps older cards (by their own `createdAt`, falling back to row time) out of the cache, peer ledger, prior-rating memory, the Hub and sharing, so old-scale numbers never anchor a new rating. Cards rated before the 2026-10-20 recalibration were moved to the RLS-locked `player_profiles_pre_recalibration` table. When you change the scale, bump the epoch and archive the same way. The 2026-10-26 rule rewrite (ability-first tiers, peer placement) deliberately kept the epoch: cards are records of when they were rated, so existing cards stay in use as rated and anchor new ones.
- Shared cards: a current card is the one shared card for `CARD_REFRESH_DAYS` (30) from its evaluation date, prime cards are frozen (except a bare "rerate <player>" command: `route.rerate` regenerates the prime card with no prior card, revision or own ledger entry in context, stamps `rerateAt`, and the `20261026120000_prime_rerate` trigger lets the newer `rerateAt` replace the pointer and archive rows; when the new window moves the evaluation date the old archive row stays, and `dropSupersededPrimes` hides it from the Hub, season lookups and prior cards; no prompt mentions it), and accepted challenges stay personal revisions logged to `dossier_revisions` (3 agreeing people re-rate early). The `enforce_dossier_refresh_window` trigger (`supabase/migrations/`) mirrors `CARD_REFRESH_DAYS`, `CALIBRATION_EPOCH_MS` and `REVISION_CONSENSUS_USERS`, so change them in both places. Inside the window only the Latest Update moves: `latestUpdateRefresh.ts` rewrites it from fresh facts once it is `LATEST_UPDATE_REFRESH_DAYS` (7) old, stamps `latestUpdateAsOf`, and writes the pointer row only (same evaluation date, so the trigger allows it).
- Versions, not legacies: a card rates one version of a player (current form, prime, or a named past season), never a career. `classifyTurn` reads a past season from the message (`requestedSeason`) and the pipeline rates that season as a `season_snapshot` card, stored only under its archive slug and found by `getCachedSeasonCard`. With no timeframe, the career status from `getPlayerIdentity` sends a retired player to his prime, and a published prime is served on that answer alone, before any grounding. A prime is a window, not one season: the stretch of consecutive seasons (at most `MAX_PRIME_WINDOW_SEASONS`, 3) when he played at his best, chosen by level rather than output, and rated at the level he sustained across it. The model returns `version.primeWindow`; `sanitizeProfileData` derives `seasonOrEra` ("2003-06") and the label from it, and a longer window fails validation. A multi-season window never answers a single-season request (`seasonMatches`), so that season gets its own season card. Prime cards from before windows keep their one season and still serve as that season's card.
- Eras: a named version of a player ("PSG Neymar", "young Messi", "the Barcelona version of Neymar") is an `era` card. `classifyTurn` reads it from the message (`eraIn`, else the classifier's `requestedEra`), only on dossier requests with no season or current-form cue. The model picks a window like a prime's (at most `MAX_PRIME_WINDOW_SEASONS`, the seasons when he was most fully that version) and `applyVersionRules` stores the user's name for it in `version.qualifier`. An era is defined by its years: the card key and archive slug use the window (`neymar-jr--era--2017-20`), it lives only under that archive slug like a season card, and `findEraCard` answers a request with an era card of the same name (`toEraKey`), or after synthesis with any era, prime or season card covering the same seasons, so the first card published for those years stays the card. An era named after the club he plays for now (API-Football) is his current form unless he has retired. Era cards skip the manager lookup.
- Positions: `CANONICAL_POSITIONS` has no separate Striker (it maps to Centre Forward). `Libero` is for sweeper-era cards only: `resolveLiberoPosition` pairs it with a modern position (`Libero/Centre-Back` by default) and files it under Centre-Back on current cards.

### Frontend State
`App.tsx` manages all state via React hooks. The header's Dossiers button toggles the main view between **Chat** and **Dossiers** (`view`); the logo also returns to Chat. `DossierHub.tsx` is the one dossier browser: a "Global hub" tab (`fetchGlobalHubDossiers`, first and the default) and a "Your dossiers" tab (the local `futbolpedia-global-dossiers` list, with rename/remove/share), sharing one card grid and filter bar. A search that finds no card offers to Scout that name. Scout's panel shows only recent cards and links to Your dossiers for the rest. The edition filter splits Current, Prime, Eras and Seasons, and each card links to the player's other versions in that tab (current form, prime, eras, seasons) as chips. Era pills are blue, so a named chapter of a career doesn't read as the prime. A card's **Ask** button takes it into the chat: it adds the card to the conversation as a `dossierKey` stub and fills the input with `cardReference` ("Neymar Jr, Paris Saint-Germain era (2017-20): "), whose edition words and season keep the reply on that version. It is layered over the chat so both keep their scroll and state. `SidePanel.tsx` only reads one dossier; it has no list of its own. Opening a global card adds it to your dossiers.

Two persistence layers:
- **`localStorage`** — Conversations (`futbolpedia-conversations`), active dossiers (`futbolpedia-global-dossiers`), theme, active conversation ID
- **Supabase** — `player_profiles` (dossier cache, `player_data` JSONB), `shared_conversations` (share codes), and the shared `club_managers` and `club_snapshots` caches

On init, `App.tsx` runs a migration path: old `futbolpedia-chat-history` / `futbolpedia-all-profiles` keys are consolidated into the newer `futbolpedia-conversations` schema. A one-time purge (`services/legacyDossiers.ts`, flag `futbolpedia-legacy-purge-v1`) then drops local cards from before the current pipeline, and any card whose player and edition the shared store has never held. Conversation titles are written by Flash from the opening exchange (`services/chatTitle.ts`); a rename sets `titleSource: 'user'` and is never overwritten.

### Key Types (`types.ts`)
- `PlayerProfile` — The central data model. Contains `basicInfo`, `ratings` (overall/potential), `attributes` (25 outfield), optional `goalkeeperAttributes`, `strengths`, `weaknesses`, `playstyleAndRole`, `shortBio`, `latestUpdate`.
- `Conversation` — Wraps an array of `ChatMessage` plus the `activeProfile` and `allProfiles` at the time.
- `ChatMessage.content` is a union: `string | PlayerProfile | ReactNode`.

### Prompt Engineering (`prompts/`, re-exported by `constants.ts`)
- `scoutCore.ts` — shared scouting philosophy, Section III rating tier scale, the 25+7 attribute framework, and named protocols (A–Q: B = injury quarantine, E = stat-lock, M = temporal firewall, Q = contextual triangulation, …). Kept byte-stable as the cached prompt prefix.
- `chatPrompt.ts` — conversational scouting mandate (Section VIII) built by `buildConversationalScoutInstruction`.
- `dossierPrompt.ts` — schema-aligned calibration and synthesis workflow (Section VI).
- **No specific examples in prompts.** Guidance that shapes cards or chat prose must be descriptive: no player names, rating anchors, quoted sample phrases or jargon lists, because the model reuses them. Format specs (YYYY-YY, label templates, enum values) are fine.
- Tier bands, canonical positions, club/position normalization and attribute labels live in `constants/ratingTiers.ts` and must match `types.ts` and the synthesis schema.
