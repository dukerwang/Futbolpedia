## Deploying

The live app (futbolpedia.org, a custom domain on the Google AI Studio deployment; futbolpedia.ai.studio still serves it) is hosted by Google AI Studio and does not deploy from GitHub on its own. A change goes live in three steps, all of which are needed:

1. **Push to GitHub and merge into `main`.** The pull script copies `main` only, so a pushed branch or an open PR is not live.
2. **Run the pull script in Google AI Studio** (`sync.sh`: `degit` of `dukerwang/Futbolpedia` into the workspace, `npm install`, `npm run build`).
3. **Publish from Google AI Studio.** Until this step, the live app keeps serving the previously published build.

So when reporting that a fix is done, say whether it is merged, and remind the user that the AI Studio pull and publish are still needed before it reaches the live app.

## Environment Variables

- `GEMINI_API_KEY` — Google Gemini key. Vite injects it into the client as `process.env.API_KEY` (read by `services/aiClient.ts`); the server's `/gemini-api-proxy/*` and its snapshot builds also use it. Run locally, `server.ts` fills any variable missing from its environment from `.env.local`, then `.env` (`loadLocalEnv`), so the server has the same keys as the browser; variables already set, as on AI Studio, always win.
- `SUPABASE_SECRET_KEY` — server-only Supabase secret key (or the legacy `service_role` key), the only credential that can write `club_snapshots` and `era_snapshots`. Without it, club snapshots are built into the server's memory only and era snapshots aren't built.
- `API_FOOTBALL_KEY` — API-Football key (used by `server.ts`). The free plan can't read the current season or use `last`/`next`, so it only helps dossier grounding for past seasons and the manager cross-check; chat research uses the live routes below.
- `XI_PREDICTIONS` (set `off` to stop the XI sweep and lazy predictions) and `XI_PREDICTION_WINDOW_HOURS` (default 48) — server-only, see XI predictions
- `GATE_FEEDBACK` (set `off` to stop the correction round before the gates cut a reply; see Gates as feedback)
- `SCOUT_DAY` (set `off` to stop the daily pass) and `SCOUT_DAY_CALLS` (model calls a day, default 30) — server-only, see Scout's day
- `CARD_REVIEW_CALLS` (model calls a day for card review, apart from the scout's day budget, default 24; `0` turns it off) — server-only, see Card review
- `GAFFA_BASE_URL` (default `https://www.gaffa.live`), `FUTBOLPEDIA_READ_SECRET` — server-only Gaffa integration (see `.env.example`). The browser learns the Gaffa origin from `GET /api/gaffa/config`

Supabase publishable keys are hardcoded (safe for client exposure): Futbolpedia's in `services/dossierCache.ts`. The Supabase JS client is loaded via a `<script>` tag in `index.html` and accessed at `window.supabase`, not via an npm package.

## Architecture

### Server (`server.ts`)
A single Express server handles everything:
- `/api/football/player`, `/api/football/squad`, `/api/football/fixtures` — API-Football lookups (hide `API_FOOTBALL_KEY`), with in-memory caches for player facts and team context. `apiFootballGet` logs every refused call (API-Football answers plan limits with HTTP 200 and an `errors` field).
- `/api/live/club`, `/api/live/player`, `/api/live/table`, `/api/live/availability` — current-season facts from two free, keyless, unofficial feeds (`services/liveFootball.ts`): ESPN's site API (a club's matches in all competitions with both XIs, formation slots and subs, fixtures, league tables) and the Fantasy Premier League feed (each Premier League player's starts, minutes and output, and the injury and suspension list). Cached on the server for every user; each lookup logs a `[live]` line. Anything a lookup couldn't get comes back in `missing` with a status: `empty`, `not_covered` (no free source has it, such as injury lists outside the Premier League) or `failed`. `/api/live/club` also returns the structured `report` the situation snapshot reads, and `/api/live/table` the table's `rows` (`StandingsRow[]`) beside its `text`, which the table view draws; the writer's `get_club_recent_team` and `get_league_table` tools strip them. A player's FPL status is worded for the next match (`describeFplStatus`: "doubtful: 75% chance of playing in the next Premier League gameweek (Head injury; FPL note dated 2026-10-17)", with FPL's own note and the date it was written, so a return date FPL gives stays as FPL wrote it); the percentage and date sit in one evidence line, so the figure gate counts them as supported. The club report's injury list still prints FPL's bare note. `/api/live/availability?names=` takes `Full Name|Club` entries separated by `;` (at most 60) and answers a whole squad from the cached FPL feed in one pass, no model calls; `findFplRosterPlayer` matches by full name on the player's club, so a bare surname never picks a player (two players share one), and a name FPL can't place is left out. There is deliberately no general pass-through route: the app is public, so one would let anyone spend the key
- `/api/history/club-season`, `/api/history/player` — facts about past seasons (`services/historyFootball.ts`): Wikipedia's article on a club's season (manager, league finish, cup runs, top scorers, every squad player's appearances and goals, the top of the league table) and on a player (season-by-season appearances and goals, caps by year, honours by club), plus ESPN's results in every competition and the starting XIs of eight league matches spread across the season, for seasons from 2003-04 on (`season` parameter). Past seasons don't change, so a club season is kept for good, in memory and on disk under `.cache/history/` (it survives a restart); a player's article is kept a week, since an active player's numbers move. Each lookup logs a `[history]` line. The season in progress is refused (`not_covered`): the live routes cover it
- `/api/gaffa/config`, `/api/gaffa/connect/token`, `/api/gaffa/clubs`, `/api/gaffa/context`, `DELETE /api/gaffa/connect/grant` — Connect with Gaffa: forward the browser's grant token (never the shared secret), so a browser reads only its manager's clubs
- `/api/gaffa/chat`, `/api/gaffa/share` — Gaffa's in-app Futbolpedia panel and its Continue in Futbolpedia, behind `FUTBOLPEDIA_READ_SECRET` (Gaffa's server checks the session and club ownership first)
- `/api/cards/lookup` — which players have a shared card, as links for Gaffa's player pages (public, read-only, no ratings)
- `/api/snapshots/club/research`, `/api/snapshots/club`, `/api/snapshots/era` — build shared club and era snapshots on the server and store them with `SUPABASE_SECRET_KEY` (`services/snapshotServer.ts`); browsers read the tables but can't write them. Each logs a `[snapshots]` line
- `/api/predictions/club?name=` — a club's XI track record (see XI predictions below): scored matches, totals per kind and the pending prediction. Public, read-only, cached five minutes
- `/api/scout/journal?days=7` — the scout's day journal (see Scout's day below): the last one to thirty passes, newest first. Public, read-only, cached five minutes
- `/p/…`, `/c/<code>`, `/og/…` — shareable links (`services/shareServer.ts`). `cardPaths.ts` reads and builds the addresses (`/p/<player>` is the default card: current form rated in the last 90 days, else the prime; then `/prime`, `/era/<YYYY-YY>`, `/season/<YYYY-YY>` and dated `/p/<player>/<YYYY-MM-DD>`), `sharePages.ts` resolves them against the shared store (other spellings redirect, a store outage serves the default page rather than a 404), `shareMeta.ts` writes the page's tags between the `share-meta` markers in `index.html`, and `shareImage.ts` draws the 1200×630 preview with satori and resvg's WebAssembly build, kept in memory and under `.cache/og/` by card version. Cards carry an optional `shareLine` for the preview quote. Nothing here calls a model. In the app, the same address opens `CardPage.tsx` (the `card` view, layered like the hub): the card, its other versions, starter questions written by code (`starterQuestions.ts`), the rating history, and Save, Share and Scout. Shared cards in the Hub open their page; Your dossiers keep the side panel, since a personal revision has no address. Back and forward work through `pushState`; old `#/p/` and `#/c/` links move to their paths on load, except a shared revision, which still opens in the side panel
- `/gemini-api-proxy/*` — forwards AI Studio's redirected Gemini calls with the server-side key
- In dev: Vite is mounted as Express middleware (`middlewareMode: true`); in prod: serves `/dist`

### AI pipeline (`services/`)
`geminiService.ts` is the entry point (`sendMessageToAI`) and a re-export barrel for older imports. Each turn:
1. **Route** — `turnRouter.ts` `classifyTurn` tries 0ms regex fast paths (archive, single dossier, compare, challenge, ranking, club tactics), then falls back to a schema-enforced Flash classifier. The result is a `TurnRoute` (`intent`, `analyticalMode`, target players/clubs, search queries).
2. **Single dossier** — checks the in-conversation dossier, the saved archive, the in-memory calibrated pool, and the shared Supabase cache (`dossierCache.ts`), in that order. `dossierStore.ts` is a barrel over the dossier modules: `dossierCards` (card keys, slugs, evaluation dates), `dossierCache` (Supabase cache, versioned archive, sharing, Global Dossier Hub), `dossierContext` (history serialization, references, locked/saved/prior-rating blocks), `dossierLedger` (grep tool, peer ledger) and `dossierPatch`. Shared cards are found under the typed name, the names on his other cards, and the names `getPlayerIdentity` gives him (`groundingService.ts`: one grounded Flash call returning the name football coverage commonly uses, his full name and his career status), so "zico" finds a card published as "Arthur Antunes Coimbra". A new card is always named by that known-as name (`cardName`), so one player never gets two cards. On a miss, `groundingService.ts` gathers the card's facts with the chat research's tools (`dossierResearch.ts`) and `dossierSynthesizer.ts` generates the card with `responseSchema`. A current card reads the player's live season record (`/api/live/player`), the live data of the club it names (else API-Football's registered club), worked into a first-choice XI with the club's stored snapshot story when there is one, two dated web searches, and API-Football's bio record. A prime, era or season card reads his career record (`/api/history/player`), one web search and, for a requested season, a stored era snapshot of that season. Everything is filed in an evidence ledger, so the prompt lists what no source covers and which lookups failed, and the card puts those in `confidence.dataGaps` instead of filling them from memory. The records settle facts, never the rating: the synthesis prompt says the tier, Overall, placement and attributes stay the scout's judgment of his football, with numbers and honours as evidence read in context, so a fuller record never shifts weight onto figures. The feeds run alongside the searches; one still running `LIVE_GRACE_MS` after them is filed as too slow. Nothing here builds a snapshot. It then enforces calibration invariants deterministically and scrubs unverified manager mentions.

**Strengths and weaknesses are the player's own.** The synthesis schema asks for each strength as a title, how he does it and what it changes, and each weakness as a title, where it shows and what it cost; `cardTraits.ts` joins them into the card's `**Title:** text` lines, so stored cards stay `string[]`. The rules (`CARD_TRAIT_RULES` in `dossierPrompt.ts`) say a skill his role never asked of him, or a quality worded as a flaw, is not a weakness, that a line just as true of most players at his position isn't his, that a limitation many players at his position share can be listed when the evidence shows it cost him but is never his only weakness, and that a title is two to four plain words a fan would use. After synthesis, `reviseCardTraits` compares each title with the lines on other players' cards (the shared pool and your dossiers; his own cards don't count): a title that reads the same (`STOCK_TITLE_SIMILARITY`) as lines on `STOCK_MIN_PLAYERS` other players is rewritten about him. The same call checks every other weakness against the rules and replaces one that breaks them with a real limitation from the evidence, or drops it when there's none, but never below `MIN_WEAKNESSES` (two). A card with fewer than two weaknesses gets one particular to him added (revision id `NEW`); it can be a recurring pattern in his game rather than one match, and is never one most players at his position share. So a rewrite doesn't land on the next stock line in other words, the call is shown the titles already common across other players' cards (`COMMON_MIN_PLAYERS`) and those on other cards at his position (`takenTraitTitles`), and is told not to make the same point unless the evidence shows it is distinctively his. So every new card with a weaknesses section pays this call. A failed or slow rewrite (`TRAIT_REWRITE_TIMEOUT_MS`) keeps the card as written; rewrites log a `[CardTraits]` line. Cards rated before this check get it from `scripts/backfill-card-traits.ts`: a proposal run (`GEMINI_API_KEY`) writes every rewrite to a JSON report and a Markdown copy without touching Supabase (`--few-weaknesses` takes only cards with fewer than two weaknesses), each rewrite also sees the lines written earlier in the run for players at the same position, and `--apply <report.json>` (`SUPABASE_SECRET_KEY`) writes the reviewed lines to every row holding that card, only where the row still holds the lines they were proposed from. The refresh-window trigger lets the secret key's `service_role` change a card's strengths and weaknesses and nothing else (`20261113120000_card_trait_rewrites.sql`), so frozen primes and archive rows can be backfilled while browsers still can't touch them.

**Ratings are the model's judgment of footballing ability.** Overall is never computed from attributes. Tiers (`constants/ratingTiers.ts`, Scout's Code §II) describe how good a footballer a version is on one all-era standard; positional rank, honours and dominance of an era are evidence, never the band itself. While rating, the model fills `calibration.peerPlacement`: which `<calibrated_peer_ledger>` peers this version was better than, level with, or not as good as. `ratingPlacement.ts` resolves those names to ledger cards (same edition preferred, never the player himself, ambiguous names ignored) and moves the Overall into the range that placement allows (strictly above/below when integers leave room, a tie otherwise). A self-contradictory placement changes nothing. The resolved placement is stored on the card (`peerPlacement`), shown under the benchmark, and serialized for chat.
**Scout panel and @ mentions.** Ratings start in the Scout panel (`ScoutDesk.tsx`, opened by the header's Scout button or ⌘K), not in chat. You type or paste names, pick Current, Prime, Era or Season (Era and Season open a field for the era or season; a version typed with the name, such as "PSG Neymar" or "Henry 2003-04", sets the switch itself, `scoutRequest` in `ratingCommand.ts`), and each name becomes a queued job that `App` runs two at a time through `ratePlayer` (`geminiService.ts`). `ratePlayer` builds the route with `routeForRating` (`ratingCommand.ts`) and runs the same `rateDossier` a typed rating reaches, with `ratingTask` as the message, so caching and editions behave identically. Finished cards land in your dossiers, and **Ask** puts one in the chat box as a mention. Typing `@` in chat lists cards only: your dossiers and the shared cards from `fetchCardIndex` (`dossierCache.ts`, a field-only select cached 10 minutes), ranked by `playerSearch.ts` (`PlayerPicker.tsx`). A mentioned card joins the conversation, and the model reads each mention as `cardReference`, so the edition carries over. Typed "rate X" still works as a chat turn.
3. **Everything else** — `conversationalScout.ts` handles rating challenges (structured patch → `applyDossierPatch`) and prose turns (comparisons, debates, rankings, tactics). A prose turn that needs live facts researches first (`researchAgent.ts`); a thread about primes, past seasons or a past decade goes through the debate brief instead (see Questions about the past below):
   - **At once, in parallel**: each spotted club's live data and stored snapshot; for a club with no fresh snapshot, its research pass (shared with the build that stores one); a web search on the question itself, unless every club already has today's snapshot; and the brief. A message that `looksLikePresentQuestion` starts that search in `sendMessageToAI` while the turn is still being routed (`startQuestionSearch`), so the classifier's couple of seconds aren't on the critical path; a wrong guess costs one search, never time. The players the router spotted get their season record at once, and a record naming a club the turn hasn't opened opens it, so the snapshot covers the club he actually plays for. The brief waits at most `STORED_PEEK_MS` for stored snapshots. A grounded web search takes about 9 s on Flash, so research runs inside a budget: nothing that has to wait for the brief can include a search and still finish inside it. On Hydrogen a grounded search averaged 14 s, with more queries per search.
   - **Brief** (one Flash call, low thinking, about 5 s; medium took about 12 s): reads the user's need (see Reading the need below), works out what the question needs, and for a question about the present puts change at the centre (`focus`: what is distinctive about this team or player this season and why). It outlines the answer and plans further lookups from typed tools (`researchTools.ts`), each tagged `facts` or `analysis`, and is told what's already running so it doesn't repeat it. The brief and reflect prompts carry `RESEARCH_COVERAGE_NOTE`, which says what no source covers and how to work around it, so the planner searches team news instead of asking again for an injury list that doesn't exist.
   - **The brief's lookups**: live feeds (`/api/live/*`: a club's results, last four competitive XIs with positions and, for Premier League clubs, season starts and the injury list; a Premier League player's season; a league table) and stored cards always run. A web search runs only if it can finish (`SEARCH_ESTIMATE_MS`) before `RESEARCH_DEADLINE_MS`; otherwise it's filed as not started. Both follow the search model's `searchLatencyMs` (8 s on 3.8 Flash, 14 s on Hydrogen), as do `REFLECT_CUTOFF_MS` and `SITUATION_CUTOFF_MS`, so the deadline is 9 s on Flash and 15 s on Hydrogen. Analysis searches wait briefly for the feeds, then run with the live facts (`formatFactContext`) so the digest flags sources describing an earlier team. Every web digest dates its points by the source's publication date. At the deadline research stops waiting. A lookup still running is set aside: if it finishes while the snapshot is being built, the writer still gets it; otherwise it's filed as too slow (a `slow` gap, as is a search not started for lack of time). A club research pass still running finishes for its build.
   - **Club snapshots**: the clubs the router spotted, and the brief's club lookups, go through `clubSnapshots.ts` (see Shared club snapshots below). A fresh stored snapshot is read before the brief (up to `STORED_PEEK_MS`) so it plans around it.
   - **Situation alongside the brief, then reflect**: on a turn about the present, the situation snapshot starts as soon as its inputs are in (the club feeds, each club's stored snapshot or research pass, the spotted players' records), so it runs while the brief does rather than after research. Clubs the brief adds later get what code works out for them. A reflect call (low thinking; skipped when research ran to the deadline or past `REFLECT_CUTOFF_MS`) reads the lookup log (`formatLookupLog`: found, empty, not covered, failed), discards web entries from earlier seasons that the live facts contradict (`discardEntries`, web only), and may add one round of up to three quick lookups (a search only while the turn is well inside its budget). The situation snapshot (`situationSnapshot.ts`) turns the evidence into a dated picture of the present: code works out each club's first-choice XI from recent starts and season starts (recent matches weigh more, domestic cups half, injured players never picked, an even split named only when another player started there at least twice and as often), who's out and recent form; one low-thinking call adds what changed since last season, what's distinctive, players' current situations and what's still unknown. A stored snapshot's story replaces that call for its club; past `SITUATION_CUTOFF_MS` the snapshot is code only.
   - **Writer**: reads `<user_need>` first, then `<situation_snapshot>`, then the evidence ledger (`evidenceLedger.ts`: numbered entries, gaps grouped by status, web entries tagged when every source predates the season) as `<factual_foundation>`, and the brief as `<research_brief>`, at low thinking since the planning is done. It argues from the snapshot and commits to one starter per role, naming an alternative only for an even split. It runs at low thinking on every prose turn (medium held the first token back by 15 s or more on card debates). It has `get_league_table` alongside the other live tools, and is told which cards the turn already looked for and didn't find, so it doesn't spend a tool round on them. It keeps its full tool set (`proseToolMode`), so it can look up what research missed; only turns answered from stored cards or the archive are limited to local tools. A follow-up in the same thread reuses the last snapshot. The chat prompt separates facts (only from the snapshot, ledger, tools or cards; say plainly when something can't be verified) from judgment (decisive), and counts precise figures (statistics, fees, percentages, table positions and points, minutes of events, shirt numbers, quotations) as facts. On a researched turn, `figureGate.ts` checks every precise figure in the reply against the turn's evidence (snapshot, ledger, cards, the writer's tool results, the conversation, and passages its own search grounded): a figure counts only when the same number sits beside the same kind of word. An unsupported figure takes its sentence with it (in a table, only its cell), on the stream and the final reply; removals log a `[FigureGate]` line. A removal never leaves a fragment: a list item left with only its marker or a label goes, and when a removed first sentence carried an item's bold label, the label's name (without its bracketed details, where a fee or count sits) moves to the rest of the item, or to the next item that opens on a pronoun, so nothing is left reading "He ..." with nobody named. Each step logs a `[Perf]` line.

   The design and later phases are in `docs/superpowers/specs/2026-10-31-agentic-research-harness-design.md`; `docs/superpowers/evals/live-questions.md` is the question set, and `npm run eval:live` (`scripts/eval-live-questions.ts`) runs it through the pipeline in-process and has a grader model with Google Search and the live feeds score stale facts, invented facts, whether the answer says what changed, decisiveness and hedged roles. The grader is the same Flash model that writes the answers, so compare runs with each other rather than reading scores as absolute. Supabase isn't loaded outside the browser, so a plain run measures cold turns; `--warm` answers each question once first to measure turns that reuse snapshots. Reports go to `docs/superpowers/evals/reports/`.

**Questions about the past.** A thread about past seasons, primes, eras or all-time comparisons (`threadIsHistorical`) runs `runDebateResearch` (`debateBrief.ts`) instead of the live research:
   - **Debate brief** (one Flash call, low thinking, temperature 0; for a new chat whose message `looksLikePastQuestion`, `startDebateBrief` starts it before routing, without the cards, unless a settled debate exists for its words): what the question turns on (`criterion`: peak level, sustained level, output, influence, versatility, or mixed), two to four criteria that settle it, each with the one figure (if any) that decides it, described by what it counts, its competition and its span but not its value (`debateFigures`), the versions compared (the windows on their cards, or club seasons), where the honest disagreement lies, the strongest counter-case, a committed verdict (or an order, for a ranking), and up to `DEBATE_CALL_LIMIT` lookups for only the facts the verdict depends on: `club_season` and `player_career` (the history routes), cards, and the odd web search. The prompt lists the cards in play in rating order with their peer placements, and gives only the history tools (`HISTORY_TOOL_GUIDE`).
   - **Late brief**: a brief not back within `BRIEF_WAIT_MS` (an outlier took 28 s), or one that fails, gives way to `cardBrief`: the cards' order as the verdict or ranking (level cards leave a head-to-head open), the named players' career records, and no figures. It's never stored as a settled debate.
   - **Card check** (`debateConsistency.ts`, code): when the question turns on how good the players were (peak level or mixed), a ranking's carded entries are put in card order (Overall, then peer placement, then the brief's order; uncarded entries keep their places) and a head-to-head verdict goes to the side whose card is above. Level cards leave it to the criteria. What moved is passed to the writer as `cardNotes`.
   - **Settled debates**: a new chat's checked brief is kept for the browser session (`liveDebateRecords`) under the question's words (filler dropped, order and case ignored, `debateSignature`) and the cards' fingerprint, so the same question, with the same cards, reuses its verdict and skips the brief call. A re-rated card changes the fingerprint and reopens it. Follow-ups in a thread always write a new brief. Debates aren't stored in Supabase: the brief is written in the browser, so the server can't vouch for it, and a shared row would let anyone set the verdict every user gets. Across sessions, consistency comes from the card ratings.
   - **Records and era snapshots**: the named players' career records start while the brief is written (`prefetchCareers`) and are handed to its matching calls; the lookups run in parallel, and a web search gets `SEARCH_BUDGET_MS` beyond the records before it's left out of the turn (a grounded search takes 9 to 13 s); each club season or player window looked up reads its stored era snapshot (see Shared era snapshots below) and starts a background build for at most `MAX_ERA_BUILDS` (one) that nobody has built.
   - **Writer**: gets `<debate_brief>` (criteria in order, versions, disagreement, the best point for the other side, the settled verdict or order, card notes, the cards' order) as its reasoning, not a layout: it first works out what the latest message asks, gives the brief's answer early in plain conversational prose explained through the criteria, gives the other side its due in a sentence, and writes no labelled criterion, counter-case or verdict sections (`PAST_DEBATE_RULES`). A brief of kind `other` (a follow-up that questions the last answer, the cards or versions it used, or a fact) gets `PAST_CONVERSATION_RULES`: answer the point directly, admit a mistake in a sentence, stop. When a player asked about in his prime has only a current-form card (`editionGaps`: in a prime thread, unless the message asks only for his current form; on any turn, when the message names his prime, however the router read it, `wantsPrimeOf`), the brief and the writer are told his prime has never been rated, so his current card is never presented as his prime, and the reply offers `prime <name>` to Scout (`offerPrimeScout`, queued as a prime rating by `scoutOfferRequest`). It quotes only the figures the brief chose, each where it decides its criterion and as `<factual_foundation>` or a card gives it, with its competition and span intact (a league figure stays a league figure, a total stays a total, a count for named seasons is never a career total); every other point is made in words. It keeps every fact to its own season, and names a past coach only from the evidence. It reads cards with local tools and gets the full set only when a lookup failed or was too slow (`writerNeedsNetwork`). Web entries aren't tagged as predating the season, the manager gate and today's coach lookup are skipped (they'd rewrite a past coach as "the current setup"), and the figure gate runs scoped and on a budget: tables in the evidence are read by their columns in place (`expandTables`), titles and trophies count as figures, each figure's qualifier (league, all competitions, a cup, Europe, international) must not conflict with the one named beside its number in the evidence and its season must not conflict with the evidence line's or its source heading's (`scopeOf`; evidence that doesn't say passes), and beyond `figureBudget` (the chosen figures, with room for each one's counterpart) the sentences with figures nobody chose go, from the end. A figure counts as chosen only when its noun, competition and season fit a chosen one, and a tally from one match fits only a slot about a match (`matchesSlot`). On these turns honour counts with longer phrasing ("four consecutive ... awards", selections, finals) and counts written as words are figures too; the live gate leaves them alone.
   - `docs/superpowers/evals/historical-questions.md` is the question set; `npm run eval:live -- --set historical` runs each question twice through the pipeline with the shared cards read from Supabase through a read-only client (`scripts/eval-history.ts`), and the grader scores blended seasons, myths, use of criteria, the counter-case and decisiveness, then compares the two runs, and each paraphrase pair, for the same verdict. Figures get their own check: one call lists every precise figure an answer states, and a second checks each with search (a one-pass grader passed them all). `--regrade <report.json>` reruns that check on saved answers, and `--no-builds` keeps a small run from paying for era snapshot builds. Every eval spends the project's Gemini budget, which the live app shares: estimate it and run the smallest subset that answers the question.

**Reading the need.** No stage used to ask what the user is trying to do, and the gap rule had become the scout's answer to pushback (`docs/superpowers/specs/2026-11-17-intent-and-conduct-design.md`). Both briefs, the research brief and the debate brief, now read the need in the same call that plans their lookups (`need`, `services/userNeed.ts`): `goal` (what the user is trying to decide or do, with the sense a knowledgeable friend brings to what they own, can do next and have said), `settle` (what a useful answer has to settle), and on a follow-up that pushes back, `objection` and `objectionFact` (the checkable fact it rests on). A disputed fact is checked this turn, never settled on the user's word: the brief plans the lookup, and a brief that records one and plans none gets the obvious lookups from code (`ensureObjectionCheck`: the spotted players' season records and clubs' recent teams, else a search on the fact; `ensureDebateObjectionCheck` on the debate path). The writer reads the need as `<user_need>`, its first block (`formatBriefNeedForWriter`, or `formatNeedForWriter` from the debate brief), passed whenever the brief exists. Deep mode has no brief: `deepModeRules` tells the loop the same in prose. The conduct rules sit in the system prompt every chat path shares (`CONVERSATIONAL_SCOUT_MANDATE`: **Reading the User** and the reworked fact and pushback bullets): answer the need, find a challenged fact now and correct the earlier reply in a sentence, never concede without checking or answer with an apology alone, read partial evidence (a status, a percentage chance of playing, a dated report) as an answer, and call a fact unverifiable only after the evidence and the tools come back empty. Replies never describe their own lookups, searches, timeouts or tools. `presentFactRules`, the brief's unresolved line and the past-debate rules say the same in short. A lookup still running, or never started for lack of time, when the answer began is a `slow` gap (`ToolOutcome.slow`), printed under **[Not back in time]** as unchecked rather than unverifiable, and the writer has its tools for it; the lookup log keeps it as `failed`, and the other headings are unchanged. Card synthesis has no tools, so `dossierResearch.ts` keeps its too-slow outcome as it was. The live set's **Conversations** section holds multi-turn cases (the shared conversation `/c/W8BVT5`, pushback on a lineup and on a past fact, and a need that differs from the words) as JSON blocks; `npm run eval:live -- --conversations` replays each tested turn with its recorded history (or chains from live answers where none is recorded), and a conduct grader checks its must-do list and three universal checks (`scripts/eval-conversations.ts`). C1 needs a Gaffa club: `EVAL_GAFFA_CLUB=<leagueId>/<clubId>` with `FUTBOLPEDIA_READ_SECRET`, so no manager's ids sit in the repo. None of it has been run live yet.

**Gates as feedback.** The three post-write gates hold a reply to the turn's evidence by deleting or rewriting what they flag, and the model never learned which claims it couldn't support. When they flag something and the turn has time, the model now gets one correction round before anything is removed (`services/gateFeedback.ts`). The gates' standard doesn't change: a rewrite stays only if the same checks, run again, pass it.
   - **What each gate returns.** Each keeps its plain form and gains one that also reports what it found, without changing what it removes or rewrites. `gateFigureFindings` (`figureGate.ts`; `gateUnsupportedFigures` returns the shape it always did) lists each unsupported figure with its kind, the sentence (or table cell) that carries it, where that starts, and the nearest evidence (`nearestEvidence`: up to three lines holding a figure of the same kind, beside the same noun for a count, that share words with the sentence; none for a quotation or when nothing fits). A figure cut only because the reply quoted more than its budget isn't a finding. `reconcileDossierNumbers` returns `findings` beside `corrections`: each misquoted attribute with the card's player, its label, the stated and the stored value, and the sentence. `scrubUnverifiedManagerTextDetailed` (`managerMentions.ts`) returns each name it replaced, with the verified coach (null when the turn verified none) and, for a club's predecessor, the club. `sanitizeScoutProseDetailed` (`conversationalScout.ts`) returns the sanitized text exactly as `sanitizeScoutProse` does, the stripped reply, and all three gates' findings read against that stripped reply, so they point into the one text a correction rewrites. `segmentReply` is the figure gate's own split into sentences and cells, shared with the round.
   - **The round.** `correctReply` sanitizes the reply; with nothing flagged it stops there (no call). Otherwise it sends one call on the chat model at low thinking, in a fixed JSON schema: the reply, then up to `GATE_FEEDBACK_MAX_FLAGGED` (8) flagged sentences, each with why (no source for this figure; this attribute reads X on the card; this coach isn't verified) and the evidence available for it (the nearest lines; the stored value; the verified coach or none). The prompt (`buildFeedbackPrompt`) is descriptive and names no player or club. The model returns replacements keyed by the exact original sentence; an empty replacement drops it. Code applies them to the stripped reply (`applyReplacements`), so every unflagged sentence is byte-identical; an entry for a sentence that wasn't flagged, a table-cell replacement with a pipe or line break, and one far longer than its sentence are ignored. A dropped sentence is cut by the figure gate itself (`drop` and `dropOnly` options), so it leaves no fragment: a list item left with only its label goes, and a label moves to what is left. Then every gate runs again on the result, and whatever is still unsupported is removed exactly as before. A failed, malformed or slow (`GATE_FEEDBACK_TIMEOUT_MS`, 8 s) call, or a second pass that comes out empty, keeps the gated reply; a failed call logs `[GateFeedback] failed ...`.
   - **Where it runs.** Deep mode always, counted against the loop's lookup budget: a round that is called counts as one lookup (`DeepStats.calls`, also when the call fails), and it is skipped when the lookups or the time budget are spent. The stage pipeline only on a turn that researched (a debate turn counts) and whose writer finished inside `GATE_FEEDBACK_CUTOFF_MS`, which is `REFLECT_CUTOFF_MS` measured from the writer's start (reflect measures it from the turn's start, but research alone uses most of that time before a reply begins; the same mark says a stage that has run long gets no optional call). Never when nothing was flagged, on a turn with no figure check, or with `GATE_FEEDBACK=off`; the challenge path, which has no figure check, is unchanged. The stream still shows the gated text as it always did; the correction runs on the final reply under the stage label "Checking the figures...", and the final reply replaces the streamed one.
   - **Measurement.** Every finished round logs `[GateFeedback] flagged N, fixed M, dropped D, removed R (ms)`: `fixed` is a flagged sentence the model rewrote that survived the second pass, `dropped` one the model removed, `removed` one the second pass still cut (a rewrite that stayed unsupported, or a sentence the model left alone). A flagged coach or attribute sentence the model left alone and the gates fixed in place counts in none of the three (`left` in the stats object). The counts are added to the turn's `[Perf]` lines (`gate feedback: ...`, and the `deep turn` summary) and to `DeepStats.gateFeedback`. `npm run eval:live` reads them into three report columns, Gate fixed, Gate dropped and Gate removed, and a total line, so a run shows how often the model keeps a flagged figure against losing the sentence. A turn with no round shows 0, 0, 0.
   - `scripts/test-gate-feedback.ts` (in `npm test`) fakes the model, tools and clock; `scripts/test-live-chat-pipeline.ts` runs the stage path's round end to end with Gemini faked at fetch.

**First-choice XI.** The model draws a club's XI with `show_pitch` (see View tools under Reply blocks below); no code attaches one. `lineupView.ts` turns each `ClubCore` into a serializable `LineupView` (club, formation, basis, XI slots, who's out) through `lineupViewOf`, with no extra model call. The pitch entry draws the XI the writer argues from when the turn built a situation snapshot that holds the club (`ThreadState.situationData` keeps it, so a follow-up draws the same XI as the writer reads), else it reads the club's live report. `PitchView.tsx` is a pure SVG (attacking upward; `placeXI` puts a slot in its row by `roleRow`, spreads a row evenly in `roleCol` order, shows an even split's other player under the name and an empty disc for a slot nobody holds), drawn in its frame by `PitchBlockView`. A season-starts XI carries broad positions (D, M, F), so it lands in the same rows by count rather than in a fixed 4-3-3.

**Deep mode.** The default path for present-day questions since 2026-11-16: one model loop decides every lookup (`services/deepTurn.ts`) within a budget it is told about, instead of the stage pipeline (the code-ordered brief, reflect and situation stages the rest of this section describes), which stays as the fallback and as the Fast path. `DEEP_BY_DEFAULT` (exported from `deepTurn.ts`) is `true`; setting it `false` makes deep mode opt-in again (the toggle reads Deep) without changing anything else. The flip was decided by the twelve-question deep run in `docs/superpowers/evals/reports/2026-11-16-2010-deep-full.md` (no stale facts, two invented, "what changed" on ten of eleven, about half the calls of a cold stage turn) against the stage pipeline's best runs of 2026-11-01.
   - **Entry**: `takesDeepPath` sends a turn to the loop when it asked for deep (`wantsDeep`) unless it is about the past (`threadIsHistorical`), a rating or challenge, an archive question, has an image, or carries a Gaffa club (the panel's `noRating` turns, or a club attached in the app, whose blocks only the stage pipeline builds); every other turn takes the stage pipeline without saying so. A turn asks for deep with `deep: true`, or by default when `DEEP_BY_DEFAULT` is on; `fast: true` always says no (and wins if both arrive). A turn that asked for deep starts no question search before routing, except one that is deep only by default and might be Gaffa's, which keeps it. It reuses the turn's card lookups, Scout offers and context blocks from `sendMessageToAI`. `SendMessageOptions` has `deep`, `fast`, `deepByDefault` (overrides the constant for one turn, for tests and the eval) and `onPath` (called as each path starts, with `{ path, fallback? }`).
   - **The toggle**: one control in the composer (`ChatInput.tsx`, beside the Gaffa chip; kept only in the composer's state), with its meaning decided by the constant (`speedToggle`). Off, it reads **Deep**, its tooltip says the scout takes longer and decides its own research, and it sends `deep: true`. On, it reads **Fast**, its tooltip says the scout answers quickly from a fixed research pass, and it sends `fast: true`, which routes an otherwise-deep turn to the stage pipeline. `ChatInput` takes a `deepByDefault` prop (default the constant) so a test can render both.
   - **Fallback**: a deep turn whose loop gives up runs the stage pipeline once in its place (`runDeepWithFallback`). The loop gives up when it throws, ends with no text (`DeepFailure` reason `empty`), or spends its budget and still returns no answer (`budget`); any other throw is reason `error`. The turn then shows the stage label "Taking the standard route...", logs `[deep] fallback (<reason>): <message>`, drops what the loop attached (XIs, shown cards, Scout offers added in the attempt) and runs the stage pipeline from the start. Slowness is never a reason: a loop that runs past its budget and writes an answer keeps it. The stage run starts only after the loop has stopped, so a turn never pays for research that succeeded and then runs again. A fallback stage run offers no Go deeper tool.
   - **The loop**: one streamed conversation on the chat model (`deep` task in `modelProfiles.ts`, low thinking). Its first message carries the conversation, the cards in play (`cardsForTurn`), each spotted club's stored snapshot when fresh (read, never built), today's coaches (`<verified_managers>`), the date and season, and the last turn's research when the thread continues; no brief, reflect or situation call. Its tools (`DEEP_DECLARATIONS`) are the writer's (`get_club_recent_team`, `get_player_season`, `get_league_table`, `look_up_dossier`, `show_dossier`, `grep_saved_dossiers`), the history routes (`club_season`, `player_career`), `web_search` (research's dated evidence digest; `kind: analysis` reads its sources against the club data already in) and the view tools from the registry (`show_pitch`, `show_table`, `show_comparison`, `show_ranking`; see View tools below), which are free: they cost no lookup, search or round (a model that draws past `MAX_REPLY_VIEWS` starts spending rounds). The model decides what to call; calls in one round run in parallel through `executeCall`. A round's text streams only once it is clearly the answer (`STREAM_HOLD_CHARS`), so a preamble to tool calls never reaches the user. A round that only draws views keeps its text as part of the answer and each view sits after it; a round that calls any lookup is a preamble round, its text is dropped and its views go after the prose already kept. Each call shows a short `onStageChange` label (`stageLabel`).
   - **Budget**: `DEEP_BUDGET_MS` (120 s of research), `DEEP_MAX_CALLS` (12 lookups; the local grep and the two show tools are free), `DEEP_MAX_SEARCHES` (4, inside the lookups) and `DEEP_MAX_ROUNDS` (10). The system prompt (`deepModeRules`) states them and tells the model to stop as soon as it has what the answer needs. It also asks for thoroughness where the default path's brief enforces it: an answer about the present says what is different this season for its club or player, and one about absences reads team news as well as the injury list. Every tool result ends with an `unchecked` line and then a `budget` line (seconds, lookups, searches and rounds left); a call the budget can't cover is refused, not run. `uncheckedFor` derives the unchecked line from the ledger for the clubs and players the turn spotted, following what the sources cover: a club's recent lineups and injury list, team news where no list covers it, a dated search on what changed this season (a fresh stored snapshot covers it), and a player's season record. It only informs the model; code never forces a round for it, and when nothing is left it says so. Once any budget is spent, the next round goes out with function calling off (`FunctionCallingConfigMode.NONE`; declarations stay so the history's calls still read) and a `researchOver` note, so the model writes. Code enforces only those stops.
   - **Conduct**: every lookup is filed in an `EvidenceLedger` (`fileOutcomes`), and a club lookup brings the club's verified coach (`getVerifiedClubManagers`) as a `<verified_managers>` block. The prompt carries the shared fact rules (`presentFactRules`, `MANAGER_FIDELITY_RULE`, `proseModeGuidance` with deep's own team rule), and `sanitizeScoutProse` runs the manager scrub, the number gate and the figure gate on the stream and the reply against the ledger, the cards and every tool result. The ledger goes into `threadStateFor` as research's does, so a normal follow-up reuses it. The loop logs `[Perf] deep round` lines and a `deep turn` summary.
   - `scripts/test-deep-turn.ts` (in `npm test`) fakes the model, tools and clock: the budget line, each cap and the tool-less round after it, parallel calls, the ledger and the figure gate, the view tools (text kept from view-only rounds, views free, the ceiling, gates per segment), the thread state, the unchecked line shrinking as calls land, and which turns take the path, with the default on and off. `npm run eval:live -- --deep` runs the live set through it and adds lookups, searches, rounds and what each reply showed to the report (the stage pipeline's counts come from its `[Perf]` lines); `--stage` runs the same set through the stage pipeline, and each row says which path answered and whether a deep turn fell back. Pass one or the other, not both.

**Initiative.** Four choices about the conversation itself that the model makes on the default chat path, as writer tools (`services/aiClient.ts` declarations, handlers built by `createInitiativeTools` in `conversationalScout.ts`, plain rules in `services/initiative.ts`). Each is a call the model may make or skip; code only enforces limits and never makes the choice. `runConversationalScout` builds them when `sendMessageToAI` passes `initiative` (never on Gaffa's panel, whose `noRating` turns can't draw chips or offers; never on a challenge turn that fell back to prose; deep mode keeps its own tool set and doesn't import any of it). The turn's `<instructions>` gain one rule per tool (`INITIATIVE_RULES` in `chatPrompt.ts`, joined by `initiativeRules`), so the byte-stable system prompt is unchanged, and a tool the turn doesn't offer has no rule and no declaration.
   - **Ask** (`ask_user(question, options)`): ends the turn. The prompt says to ask only when the message reads two ways that would change the answer and nothing in the thread or the cards in play settles which (which version of a player when more than one card of him is in play, which club, which season), and otherwise to take the likelier reading and say in one sentence which it took. `validateAsk` accepts two to four distinct options (each cut to `ASK_OPTION_MAX_CHARS`) and a question; anything less is returned to the model as an error and the turn goes on, so a half-formed ask becomes an answer. A valid one sets `attachments.ask`, and `generateProseTurn` checks `endTurn` after each round of tool calls: the question is the reply (streamed, then run through the same gates), with no further model round. An asking reply drops the cards, XIs and go-deeper flag drawn for an answer and keeps scout offers. `ChatMessage.ask` is drawn by `ReplyChips.tsx` as chips under the reply, on the latest message only; one sends its text as the next user message through `handleSendMessage`.
   - **Prepare** (`prepare_club(club)`): starts the server's snapshot build, through `GET /api/snapshots/club`, for a club the model expects the thread to need next, and returns at once (the response is never awaited, and a failed build changes nothing: the next turn builds as it would have). `createPreparer` allows a club once per conversation (`PREPARE_PER_CONVERSATION` clubs in all, `PREPARE_PER_TURN` in a turn, keyed by `conversationId` and kept for the last 500 conversations), treats "Arsenal" and "Arsenal FC" as one club (`clubKey`), and leaves a club the turn already reads to the turn. Builds cost Gemini calls, so these caps are what keeps the model from spending freely. The prompt says it is for the next step of the thread, never the current answer.
   - **Offer** (`offer_rating(name, edition)`, `current` or `prime`): adds a Scout offer through `offerScout` and `offerPrimeScout`, so a player already offered, or whose card is shown, is never offered twice, and one who has a card for that version (found in the reply, the cards in play, your dossiers or the shared index) returns `offered: false`. It only offers: rating stays opt-in, and the prompt says to offer and never rate. The two code rules stay as fallbacks. The router rule in `geminiService.ts` still offers every target player with no card. The `look_up_dossier` rule offers a missing player by itself only when the user named him (`askedDirectly`: a routed target, or every word of his name in the message); a player the model looked up for its own reasons gets a note to call `offer_rating` if his card matters. Deep mode passes no filter and keeps its old behaviour.
   - **Go deeper** (`request_deeper(reason)`): offered only on a turn that ran the stage pipeline while the deep loop would have accepted the message (`takesDeepPath` with the deep flag), so its chip never leads to a turn that ignores the rerun. With `DEEP_BY_DEFAULT` off that is every such turn that wasn't sent with Deep, as before; with it on, only a turn sent with Fast. A deep turn has no chip, and neither does a stage run after a deep fallback, since the user didn't choose the stage route (a thread about the past, a Gaffa club attached, an image and the rating, challenge and archive intents are left out, tool and rule both). The prompt says to use it only when the answer had to leave something unverified or unexplored that a longer look would settle, never as a hedge, and to write the best answer anyway. The reply carries `goDeeper: { reason }`, drawn as a Go deeper chip with the reason as its tooltip on the latest message; one reruns the user message the reply answered with `deep: true` (which forces the loop whatever the constant says), as a new turn under a new user message, so the first reply stays. A message that mentioned cards reruns with its labels and without their edition wording (the cards are still in the conversation).
   - **Plumbing**: the question and the Go deeper flag are `ask` and `goDeeper` blocks, reaching `ReplyBody` through `onBlocks` and `App.tsx`, and persist with the conversation like cards and offers.
   - `scripts/test-initiative.ts` (in `npm test`) runs `sendMessageToAI` for real with the model faked at fetch. Its live check is the eval: questions 13 to 15 must never ask, and question 8 should ask which version of him when his current and prime cards are both in play. Neither has been run yet.

**Reply blocks.** A chat reply is an ordered list of typed blocks (`ChatMessage.blocks`, `ReplyBlock` in `types.ts`): `prose`, and the kinds in `ReplyBlockData` (`pitch`, `card`, `scoutOffer`, `ask`, `goDeeper`, `scorecard`). A non-prose block has an `id` and a `status` (`pending`, `ready`, `failed`); only `ready` blocks are stored. `services/replyBlocks/` holds one registry entry per kind (`REPLY_BLOCKS`): `tool?` (the Gemini declaration, on `pitch`, `table`, `comparison` and `ranking`), `hint?` (what the call tells the skeleton while it loads), `build(args, ctx)` (real data in, a block or a reason out; `ctx` carries the research toolset, evidence ledger, stored snapshots, the reply's blocks and the clock), `toolResult`, `toHistory` (a one-line stub, `[shown: …]`, that `buildHistoryContents` writes in place for a reply stored as blocks) and `toCopy` (Copy and Share; the table, comparison and ranking carry text, the pitch and cards none). A new kind is one line in `ReplyBlockData` and one entry. `ReplyComposer` (`composer.ts`) is what every chat turn writes to, in place of the old `ReplyAttachments`: prose segments with views between them (`addView` with `inline` closes the prose written so far and puts the view where the model called it; without it the view goes after the last prose, as on a reply whose text isn't streamed), pending views that settle in place, and the blocks code adds (`setScorecard` first; then after the prose the end views, cards, Scout offers, `ask`, `goDeeper`). `sendMessageToAI` creates one per chat turn, feeds it the stream (only when the caller streams), and calls `onBlocks(blocks, { cards })` as it changes and once with the final blocks; `App.tsx` stores that list on the streaming message and files `extras.cards`. A deep turn that falls back restores a composer snapshot. `blocksOf(message)` returns `message.blocks`, else builds blocks from the legacy fields (`gaffaScorecard`, `dossier`, prose, `lineups`, `cards`, `scoutOffers`, `ask`, `goDeeper`, in that order), so old conversations render unchanged and storage is never rewritten. `ReplyBody.tsx` renders them; `ChatMessage.tsx` keeps the frame. `runViewTool` runs a registry entry for a model tool call. Design: `docs/superpowers/specs/2026-11-16-chat-components-design.md`.

**View tools.** The model, not code, decides what a reply shows and where. Every prose turn on both paths is offered `show_pitch`, `show_table`, `show_comparison`, `show_ranking` and `show_dossier`, a thread about the past and a turn answered from cards included; Gaffa's panel (`noRating`), rating and challenge turns, and a Gaffa trade scorecard reply are offered none (`views` on `runConversationalScout`). `createViewTools` (`services/replyBlocks/viewTools.ts`) runs a call through `runViewTool` with `pending` and `inline` on: the composer closes the prose written so far, places a skeleton sized from the call's `hint`, and settles it in place when `build` resolves; a failed build is the tool result and draws nothing. When the reply's text isn't streamed there is nothing to anchor to, so the view follows the prose. `show_dossier` lands inline the same way. The one limit is `MAX_REPLY_VIEWS` (12), refused with "view limit reached, nothing drawn"; no rule about a kind or a subject sits under it.
   - **Data**: code fetches, the model names the subject. `show_table` reads `/api/live/table` for today (a past season is "no past tables yet") and passes its rows; `show_comparison` resolves both cards through `dossierLookup.ts` (never rating anyone; a missing card is an error the model can answer with `offer_rating`); `show_ranking` resolves up to 15 names to cards (an uncarded one is listed by name with a Scout action) and, for `peak level`, `sustained level` and `mixed`, runs `checkOrderAgainstCards` so carded entries take the cards' order, with the moves in the block and the tool result; for `output`, `influence` and `versatility` the model's order stands. `show_pitch` draws the XI of the turn's situation snapshot when it holds the club, else reads the live report.
   - **Prompt**: one descriptive line per tool (`VIEW_RULES`, `viewRules()` in `prompts/chatPrompt.ts`) joins the turn's `<instructions>` on the stage path and `deepModeRules` on deep mode, with no examples; the system prompt stays byte-stable.
   - **Gates run per prose segment.** The composer holds the reply's raw text and a gate (`setGate`); each notice reads the segments through it, and the final pass (the stage path's and deep mode's correction round included) joins the segments with a fixed heading line (`SEGMENT_MARK`, `segmentGate.ts`) the gates leave alone, so one gate pass, one figure budget and one correction call cover the reply, and splits it back (`settle`). A sentence the gates cut leaves its segment, never a view. Each view's `toolResult` joins the evidence (`toolResults`), so prose that quotes a figure the table shows counts as supported; views themselves are never gated. An `ask_user` that ends the turn replaces the prose and drops the views.
   - `scripts/test-reply-blocks.ts` covers each entry, the composer's gates and segments, the ceiling and the skeleton hint; `test-deep-turn.ts` and `test-initiative.ts` cover both paths (offered on a past thread and a card-only turn, absent on Gaffa's panel and a challenge turn, inline anchoring on a streamed reply). `npm run eval:live` adds a Views column, so a run shows which views each answer drew; its questions 1, 4, 10, 11 and 12 should reach for a fitting view and question 15 draws no pitch (unrun: it spends the shared Gemini budget).

**Chat stays on the stored cards.** A new dossier shows in chat as a one-line stub carrying `dossierKey`; `buildHistoryContents` swaps each stub for the full card, so the model sees cards where the user saw them. Challenge turns get the challenged card plus the full card of every other player in the thread (in the same edition), and the thread's earlier replies keep their closing verdicts. A follow-up with no timeframe in a prime debate stays on prime cards. A prime that a later "rerate" replaced is swapped for the shared card that replaced it before the turn runs (`replaceSupersededPrimes` in `dossierLookup.ts`), in the thread, the conversation's profiles and your dossiers, so the old window and numbers never sit beside the new card; a personal revision stays. After generation, `dossierNumberGate.ts` puts any misquoted attribute of a card in play back to its stored value; it never touches Overall/Potential, which debate prose may propose on purpose.

**Rating challenges are opt-in.** A rating is revised only when the user pressed **Challenge** on the card (the side panel's dossier view): `App` keeps `challengeCard` until the user ends it from the composer's chip or leaves the conversation, and sends its key as `challengeCardKey`. `sendMessageToAI` then routes the turn to `challenge_or_revise` on that card; without the key, a turn the router reads as a challenge is answered as a question (`player_qa` for one player), so pushback or a question about a card is never put on trial.

The chat prompt's **How cards work** section says what a card is (one version: current form, prime, an era or a season; a version has a card only once someone has scouted it; one never stands in for another), so the model answers questions about the app from that rather than inventing rules.

**Chat reads cards on its own.** "How good is <player>" is a question, not a rating: `playerQuestionSubject` routes it to chat as `player_qa`. For chat and compare turns, `sendMessageToAI` looks up each target player's card in your dossiers and the shared card index (`dossierLookup.ts`, which never rates anyone), so the model answers from it. Code shows no card by rule: the model shows the card that answers the user with `show_dossier`, where it needs it in the reply. A player nobody has rated gets a Scout offer that queues him in the Scout panel. The prose model also has `look_up_dossier` and `show_dossier` tools, and the turn returns what it showed or found missing through its blocks. A message that only mentions cards, or only asks to see them ("let me see @…", `chatIntent.ts`), posts the cards without a model turn.

`aiClient.ts` wraps `@google/genai`: `generateStructured` (schema JSON), `runGroundedSearch`, and `generateProseTurn` (streaming chat with local tools `grep_saved_dossiers` / `grep_gaffa_market` and the live data tools `get_club_recent_team` / `get_player_season`). Per-task model, thinking level and temperature come from `constants/modelProfiles.ts`.

### Gaffa club in chat (`services/gaffaTurn.ts`)
A Gaffa club is context on a native conversation, not a separate mode. **Connect with Gaffa** (`services/gaffaConnect.ts`): the composer's Gaffa chip opens Gaffa's `/connect/futbolpedia` in a popup (opened inside the click, before anything is awaited, or browsers block it); the signed-in manager presses Allow and Gaffa posts a one-time code back to this origin, or, with no opener, redirects to `#/gaffa/connected?code&state`. The browser checks the state against the attempt it started and exchanges code and PKCE verifier through `POST /api/gaffa/connect/token` for a read-only `fpg_` grant token, kept in localStorage (`futbolpedia-gaffa-grant`). `/api/gaffa/clubs`, `/api/gaffa/context` and `DELETE /api/gaffa/connect/grant` forward that token to Gaffa (`services/gaffaGrantProxy.ts`) and never attach the shared secret, so a browser reads only the manager's own clubs. A 401 forgets the grant.

The chip lists every club grouped by league; the picked one is stored on the conversation (`Conversation.gaffaClub`). A new conversation starts with no club: it gets one only when the user picks one, or when it opens from a Gaffa link (`#/gaffa/<leagueId>/<clubId>`) or Continue in Futbolpedia, and an existing conversation keeps the club stored on it (an older build's stored "last club" key is cleared on load). Connected with nothing attached, the chip reads "Gaffa" in its muted style; with a club it turns green and shows the club's name, with its league in the tooltip. A small × beside the name (its own button, "Detach Gaffa club") detaches the club from this conversation in one click without disconnecting Gaffa, and the menu's radio row "Don't use a club in this chat" does the same. In dev, `/dev/gaffa-chip` draws the chip's three states from fixture clubs, with no grant. `services/gaffaContext.ts` caches each club's `GaffaContextBag` and rereads it when it's over ten minutes old. An empty conversation with a club shows `GaffaClubWelcome` (the club line and three questions from the bag). `#/gaffa/<leagueId>/<clubId>[?q=]` from Gaffa opens a new conversation with that club once it's confirmed as one of the manager's, with the question in the box.

Each turn, `runConversationalScout` gets the bag (`gaffaBag`), except on a thread about the past. `leagueFocusOf` reads what the question asks about the club (`none`, `squad`, `lineup`, `market`, `trade`, `rules`; a short follow-up keeps the last question's focus), and `buildGaffaTurn` adds `<gaffa_club>` (club, table, matchup, Club Balance, squad) to every turn, plus `GAFFA_RULES_SNAPSHOT` for rules, lineup, market and trade, the lineup audit for squad and lineup, `<locked_market>` and the bid math for market and trade, and the trade scorecard (one model call, shown above the reply) for trade. A squad or lineup question also researches the PL clubs most starters play for. The block joins the figure gate's evidence, the writer gets `grep_gaffa_market`, and squad and market names are copied exactly (`lockGaffaRosterNames`).

**Real availability.** Gaffa's roster statuses (IR and the rest) are designations the manager chose, not medical facts. For a squad, lineup, market or trade turn, `buildGaffaTurn` reads the squad's FPL status with one request (`services/gaffaAvailability.ts`, `/api/live/availability`, cached five minutes in the browser; the server's own fetch resolves the relative URL for Gaffa's panel) and `formatGaffaClubBlock` puts `FPL: <status line>` beside every player Gaffa lists as anything but active and every player FPL lists as out, with a line saying IR is a designation and the FPL line is the real availability. A failed or empty lookup leaves the block as it was. **Bid calculator.** `wantsBidMath` also runs for cost, price, pay, afford and fee wordings; for a market question that names no player (`looksLikeGaffaMarketQuery`), it prices the top unowned players by market value (four at most) at the positions the question names, else at the starters' lowest-rated slots from the scout's cards, else at any position, and says that is what it did. **Follow-ups.** A follow-up with no cue of its own keeps the thread's last focus (looking back four user messages): always when it is up to 14 words, and past that when it names a roster player (full name or a surname of four letters or more, accents ignored) or names no other subject (`namesOtherSubject`: a capitalised word in mid-sentence that isn't the club, league or a roster name). **Manager's reasoning.** Every focus except `none` adds `<gaffa_manager_reasoning>` (`GAFFA_MANAGER_REASONING`, `constants/gaffaRules.ts`): scarce roster spots and Club Balance, one starting goalkeeper, IR as a designation to judge a signing after his return, the healthy-on-IR bid block, near-term points against the long view, the weakest starting slot as the starter who adds the fewest points, advice that respects the manager's constraints, and checking a checkable fact before advising. It names no player and carries no sample number or phrase. A club in a shared conversation that isn't one of the manager's is dropped.

**Gaffa's own panel** (`services/gaffaChatApi.ts`): Gaffa's server checks the manager's session and that the club is theirs, then calls `POST /api/gaffa/chat` with `FUTBOLPEDIA_READ_SECRET`. The server reads the club with the secret and runs the same `sendMessageToAI` turn as this app's chat, with the club attached, `noRating` (a rating request is answered as a question about the player, and the reply sets `continueSuggested`) and a `conversationId` namespaced by manager. `stream: true` answers with newline-delimited JSON events (`stage`, `text`, `scorecard`, then `done` with the prose, card links and `turnsLeft`, or `error`); without it, one JSON reply. Each manager gets `GAFFA_CHAT_DAILY_TURNS` (10) turns a day (`gaffaTurnBudget.ts`, in the server's memory, keyed by Gaffa's `userId` or else the club); a turn that fails before answering is given back, and the limit answers 429 with `turnsLeft: 0`. `POST /api/gaffa/share` (same secret) turns Gaffa's thread into a shared conversation with the club attached for Continue in Futbolpedia (`#/c/<code>`). `GET /api/cards/lookup?names=` (public, read-only, no ratings) gives each name's shared card as a `#/p/<slug>` link (`cardLinks.ts`), current form before a prime, and `#/scout?name=` opens Scout with that name in its field, unrated until you press Rate. `gaffaChatService.ts` now holds only the trade scorecard.

For the pipeline to run on the server, `server.ts` sends relative fetches (`/api/live/club`) back to itself and gives `dossierCache` a Supabase client with the publishable key (`useServerSupabase`), so the server reads cards and snapshots under the same row-level security as a browser. Follow-up state (`threadStateFor` in `conversationalScout.ts`: the last turn's research and situation snapshot) is kept per conversation, at most 500 for an hour each, so one manager's research never reaches another's follow-up.

### Shared club snapshots
`clubSnapshots.ts` keeps each club's situation (first-choice XI, absences, form, what changed since last season, what's distinctive this season) in the Supabase `club_snapshots` table, keyed by the club name the live data resolves to, like `club_managers`. A turn reads the stored row first; when it's missing, more than a day old or built under an older `SNAPSHOT_VERSION`, a build runs `researchClub` (three searches at once: changes since last season, a tactical analysis read against the live facts, and team news where no injury list covers the club) and `summarizeClub` (the situation call), then stores the snapshot for everyone. The research pass is shared with the turn that started it, which files its results as evidence instead of searching the same things. Builds start with the brief when the turn is likely about the present, are shared by concurrent requests, and a failed build is never stored (retried after 10 minutes). A turn uses a snapshot that's ready within `SNAPSHOT_GRACE_MS` of its first round; one still building finishes for the next turn. The XI, absences and form always come from today's live data; only the story is reused. Bump `SNAPSHOT_VERSION` when the snapshot's shape or build changes. The browser reads the table directly, but research passes and builds run on the server (`services/snapshotServer.ts`, `GET /api/snapshots/club/research` and `/api/snapshots/club`): it fetches the live data itself through `inProcessGet`, runs the searches and the situation call with its own Gemini key, and writes the row with `SUPABASE_SECRET_KEY`. The table has no insert or update policy (`20261101140000_club_snapshots_server_writes.sql`), so a browser can't change the facts every user's writer reads. Without the secret key, builds are kept in the server's memory.

### XI predictions
`xiPredictions.ts` keeps the scout's track record: before each match of a club with a stored snapshot, the server stores two predictions of its starting XI in the Supabase `xi_predictions` table (one row per club and ESPN match id; public read, written only with `SUPABASE_SECRET_KEY`, else kept in the server's memory, as it also is when the table's migration hasn't been applied). After the match it stores the lineup ESPN published (`parseMatchLineup`, through `live.matchLineup`) and scores both. The **code** prediction is `firstChoiceXI` as it is from today's live report. The **adjusted** prediction is one low-thinking call (`prediction` task, `generateStructured`) that reads the code XI, the club's stored story (`changes`, `distinctive`, `newsAbsences`, `unknowns`), the injury list, form, the fixture and how many lineups this season were read, so a signing with no starts or a departed player with many can be corrected. It returns the same role codes with a reason for each slot that differs; a failed, slow (`ADJUST_TIMEOUT_MS`) or unusable answer stores the code prediction alone with `adjusted_status` `failed`. The adjusted XI keeps the code XI's shape, so both share one formation. Nothing here changes what the writer reads: the record exists to decide later whether the adjusted XI should replace the code XI.

`xiScoring.ts` holds the rules, pure: names right (0 to 11, matched with `samePlayerName`, which reads names the way the live data does; a rotation alternative counts as a name hit where the first choice sat out), slots right (the same player in the same ESPN slot code; a rotation alternative never counts), formation right (null when either side has none, and left out of the hit rate). A slot with no name never scores. A prediction made at or after kickoff is scored but flagged `late` and left out of the record.

The sweep (`sweep()`) is something the server runs on start and hourly (`setInterval`, unref'd, never overlapping). For every club with a snapshot built in the last `XI_SNAPSHOT_MAX_AGE_MS` (14 days, so a club nobody asks about stops costing calls) it reads the live report through `inProcessGet`, scores finished unscored matches (two hours after kickoff, given up on after 14 days), then stores both predictions for each fixture kicking off within `XI_PREDICTION_WINDOW_MS` (48 hours) that has no row. The same two steps run for one club, off the request's critical path, when `/api/live/club` or `/api/snapshots/club` is asked about it (`lazy()`, at most every 30 minutes per club), since browsers read the snapshot table directly and the server sees only those routes. One run per club at a time, so the sweep and a lazy run never predict a match twice. Every run logs a `[predictions]` line with counts.

Budget: one Flash call per club per match, only for clubs with a stored snapshot, and at most `MAX_ADJUSTED_PER_SWEEP` (25) per sweep (3 per lazy run); fixtures beyond it wait for the next sweep. A dev server with the secret key in `.env.local` writes real rows and spends real calls, so set `XI_PREDICTIONS=off` there; without the key, only clubs built in that process are swept. `GET /api/predictions/club?name=` returns `scored` (newest first, each with both predictions, the actual lineup and the scores), `totals` per kind plus `paired` (both kinds over the matches that have both, the fair comparison), `pending` and `lateExcluded`.

### Scout's day
`scoutDay.ts` is the one place the server decides what to research between conversations, and the model, not code, makes the choice. Once a day one planning call reads a dated summary of signals code gathered and returns a ranked list of actions; code runs the list with the builders the app already has, within a call budget it enforces, and writes the pass to a journal row.

**Signals** (`gatherSignals`, sources injected, each guarded so one failing source is listed under `unread` and the rest still count; every list is capped at twenty names, most asked about first):
- *Demand*: the clubs, players and club seasons the server's routes resolved in the last seven days. `createScoutTally` counts hits from `/api/live/club`, `/api/live/player`, `/api/snapshots/club`, `/api/snapshots/club/research`, `/api/predictions/club` and `/api/history/club-season` by the name the live data resolved, never by what a user typed, and a Gaffa chat turn as a bare count (the clubs it researches arrive through the live routes). The tallies are in memory, so **a restart loses them**: the summary says how many hours it has been counting, and the first pass after a restart plans from a thinner picture.
- *Prediction record*: clubs with a stored snapshot whose latest scored XI prediction missed by three or more names (`STALE_MISSED_NAMES`), taking the adjusted kind when it exists, since it reads the club's story, else the code kind. A miss marks the story as stale.
- *Fixtures*: clubs with a stored snapshot that play within 48 hours, and whether the snapshot is more than a day old.
- *Cards*: current shared cards (pointer rows of `player_profiles`, read with the server's client) whose evaluation date is within three days of `CARD_REFRESH_DAYS`, and cards past `LATEST_UPDATE_REFRESH_DAYS` on `latestUpdateAsOf`. Primes, personal revisions and cards past their window never appear.
- *Gaps*: the `missing` entries with status `empty` or `failed` that found club lookups and history lookups returned, tallied by item text. `not_covered` is not a gap to fill, and a lookup that found nothing records nothing, since its item names what was typed.

**The plan** (`PLAN_SCHEMA`, `generateStructured` on the `prediction` task's low-thinking tuning): the prompt carries the date, the season, the remaining budget (the day's calls less the planning call), what each action costs, and the signals; it says to prefer what people ask about and what the record shows is stale, to use only names the signals show, and to leave the budget unspent when nothing is worth it. The prompt names no club or player. The answer is one summary line and at most twenty actions, each with a one-line reason, from a typed set:
- `rebuild_snapshot(club)`: replaces the club's stored snapshot with a new build (`SnapshotServer.rebuild`, about four calls: the research searches plus the situation call).
- `build_era(club, season)`: a permanent club-season snapshot (`SnapshotServer.eraBuild`, three calls); a season already stored costs nothing. Only a single past season from 2003-04 to last season.
- `refresh_latest_update(player)`: rewrites a current card's Latest Update (about two calls) and writes the pointer row with the secret key; the refresh-window trigger allows it because the card keeps its evaluation date inside its window, and the row is read back to confirm the write wasn't skipped. Only a player the signals list as having an old line.
- `research_note(subject, question)`: one grounded search with the dated evidence digest, kept as a row in `scout_notes`.
`sanitizePlan` drops unknown action types, actions without a reason, clubs or players the signals don't support, seasons that aren't past seasons, repeats and everything past twenty.

**Budget and off switch.** `SCOUT_DAY_CALLS` (default 30) covers the whole pass, the planning call included. `executePlan` runs the actions in order, charging each its real call count (a thrown action is charged its estimate, and doesn't stop the pass; a Latest Update refresh is charged its estimate because the rewrite doesn't report its calls). An action whose estimate no longer fits is skipped with the reason, and a cheaper one further down may still run. `SCOUT_DAY=off` stops the pass. Without `SUPABASE_SECRET_KEY` it doesn't run at all, since nothing it finds could be kept, and logs why; it also doesn't run until the `scout_journal` table exists.

**Schedule.** An hourly tick (unref'd, never overlapping) runs the pass once per UTC day, after the first prediction sweep, and on start when today's hasn't run. A day with a `done` journal row is never run again, across ticks and restarts. A `running` row left by a pass that died (untouched for 15 minutes) is resumed from its stored plan with the calls already recorded, not re-planned. A failed planning call is retried on later ticks, three times in all, then the day is journaled empty with the error.

**Notes as evidence.** `scout_notes` (`20261116120000_scout_day.sql`) holds subject, question, dated digest, sources and day; public read, written only with the secret key. `researchAgent.ts` files, after its research round on a turn about the present, every note from the last 14 days (`SCOUT_NOTE_DAYS`) for the clubs it opened and the players it looked at as a dated `scout_note` evidence entry (`scoutNotes.ts`, at most four, newest first), so the writer reads it as `<factual_foundation>` and the figure gate counts its figures as supported. A slow or missing table leaves the ledger as it was. No prompt mentions notes.

**Journal.** `scout_journal` has one row a day: `signals`, `plan` (summary and actions with reasons), `ran` (each action with its calls, outcome and time), `skipped` (with why), `calls_spent`, `budget` and `status`. `GET /api/scout/journal?days=7` returns the last rows, newest first. The row holds counts and names the live data resolved, never user text.

Every pass logs `[scout-day]` lines: the signal counts, the plan with each reason, each action's outcome and calls, what was skipped, and calls spent against the budget.

### Card review
`cardReview.ts` is the scout's day for players: it finds the cards whose facts or rating no longer hold and re-evaluates them under the card rules. It runs inside the scout's day pass, with the same planning call, on its own budget line, `CARD_REVIEW_CALLS` (default 24), so card work never starves snapshots: `executePlan` charges card actions to the card line and every other action to the day's, and the journal row keeps both (`card_budget`, `card_calls_spent`). It needs `SUPABASE_SECRET_KEY`.

**Signals** (`gatherCardSignals`, added to the day's summary under `cardReview`; each list capped at twenty):
- *Past the window*: current cards whose `CARD_REFRESH_DAYS` window has closed, queued ones first, then the most asked about. Demand adds card views to the live player route: `createScoutTally().cardView` counts card pages served on `/p/` (`onCardPage` in `shareServer.ts`) and `/api/cards/lookup` names that resolved to a card.
- *Moved inside the window*: current cards whose live player record names a different club, or whose club's stored snapshot XI no longer has him while the card rates him at least an everyday starter (`STARTER_MIN_OVERALL`, the Quality Starter band). Only the Latest Update can change inside the window, so the plan may refresh it now (`refresh_latest_update` runs for these whatever the line's age), and the card is listed as queued, read back from the last month's journal rows, on the day its window ends. At most `SITUATION_CHECKS` (60) cards are checked a day.
- *Covered gaps*: prime, era and season cards whose `confidence.dataGaps` name a season or club that an `era_snapshots` row or a history cache entry (`.cache/history/`, by file time) covers, built after the card was rated (`coverageFor`).
- *Coherence*, by code over the served pool (`findCoherence`): pairs of cards whose placements put each above the other (either card's `betterThan` or the other's `notAsGoodAs`), three cards whose placements go round in a circle, and each position's Overall distribution against the pool, reported as a figure only.

**Actions** the planner may choose (`sanitizePlan` keeps only names and card keys the signals give; the prompt says a rating is re-examined only for a reason the signals give):
- `rerate_current(player)`: `ratePlayer` on the server, the same pipeline a visitor's Rate reaches, so the new card publishes exactly as their request would (about eight calls). The card is confirmed by reading the pointer back, since the pipeline doesn't await its write.
- `fill_facts(cardKey)`: one extraction call reads the card's gaps and the stored record and returns the facts it settles; code removes those gaps from `confidence.dataGaps` and records each in `filledGaps` (gap, fact, source, day), in place on the pointer and archive rows, with the rating untouched (estimated at two calls).
- `review_prime(player)`: a prime rerate drafted with the reason and its evidence in the synthesis task (`draftPrimeRerate` in `geminiService.ts`, which runs `rateDossier` with `hold` so nothing is written), then reviewed (about nine calls a round). A prime draft is never written before its review.

**Self-review.** Code checks each draft first (`guardDraft`): the edition and player, a window of at most three seasons, the Overall inside the range the draft's own placement allows against today's pool, and no move across more than one tier band without a new record or a contradiction in its evidence. Then one schema-enforced call on the `review` task (a thinking level above synthesis, since nothing waits on it) reads the published card, the draft, why the review was opened with its evidence, and the neighbouring cards (same position, Overall within three), but not the drafting conversation. It answers four checks (driven by the evidence, the rules hold, figures supported, a proportionate move) and a verdict. `sanitizeReview` turns an accept with a failing check into a revise (or a refusal on the last round), and a revise on the second draft into a refusal. `accept` publishes through the rerate path (`rerateAt`, `upsertCachedDossier` with `supersede`), confirmed by reading the pointer back; `revise` allows exactly one more draft with the notes in its task, when the card budget can cover it; `refuse` publishes nothing.

**Writes.** `dossierCache.useServerSupabaseWriter` gives the shared cache a separate secret-key client for writes (`upsertCachedDossier`, `publishLatestUpdate`); reads stay on the publishable client. Every write crosses `enforce_dossier_refresh_window`: a new current card replaces one past its window, a prime pointer or archive row changes only for a newer `rerateAt`, and the service-role clause allows in-place changes to strengths, weaknesses, `confidence.dataGaps` and `filledGaps` (`20261116150000_card_fact_fills.sql`) and nothing else. `fill_facts` reads each row back, so a skipped write is reported in the journal rather than assumed.

**The trail.** Every re-rating is a `card_reviews` row (`20261116140000_card_reviews.sql`; public read, written only with the secret key): the card key, the old card, the last draft, why it was opened, the verdict and reasons, each round, revise notes, and what published when. A current re-rate is recorded with verdict `rerated`. Each action's journal entry carries the card's Overall, tier and dates before and after. A turn files the latest published review from the last 90 days for each card in its ledger and each player it is about as a dated `card_review` evidence entry (`cardReviewNotes.ts`, called from `researchAgent.ts` and `debateBrief.ts`), so chat can say why a rating changed from the record. No prompt mentions it.

### Shared era snapshots
`eraSnapshots.ts` keeps permanent snapshots in the Supabase `era_snapshots` table (`supabase/migrations/20261101130000_era_snapshots.sql`): a club season (coach and usual XI, shape and style, record, what defined it, figures copied from the sources, and claims often misstated) and a player's window (role, clubs, coaches and teammates, honours and output, the same figures and misstatements). Each is keyed by the Wikipedia article its facts came from and the normalized season or window, so "Arsenal" and "Arsenal FC" share one. The first turn that looks one up asks the server to build it in the background (`GET /api/snapshots/era`, `services/snapshotServer.ts`). The server fetches the record itself and runs `buildEraSnapshot` only when it can store the result (`SUPABASE_SECRET_KEY` is set and the table exists; otherwise every later question would pay for the build again): the record it already fetched, two searches read against it, and one medium-thinking call that writes only from that evidence. Later turns read it as an `era_snapshot` evidence entry. Concurrent requests share a build, and a failed build isn't stored (retried after 10 minutes). Browsers can read the table but not write it: its only policy is public read, and the server writes with the secret key. Rows are kept for good: the `keep_era_snapshots` trigger skips any update that doesn't carry a newer `version`, so bumping `ERA_SNAPSHOT_VERSION` rebuilds every row.

### Manager fidelity
API-Football and model memory both lag coaching changes, so neither decides who manages a club. `services/clubManagers.ts` looks it up live: a focused Google-grounded Flash search per club (coach, appointment date, immediate predecessor, source), cross-checked against API-Football's `pickCurrentCoach` record (the search wins a disagreement; no search answer means nobody is named). Results are shared through the Supabase `club_managers` table and refreshed at most once a day per club. Nothing is maintained by hand.
- **Cards:** the dossier prompt forbids manager names in card prose. After synthesis, `attachVerifiedManager` sets `profile.clubManager` (shown on its own "Manager:" line of current cards, with its verified date) and scrubs the prose in strict mode, so only the verified coach can be named, and nobody when the lookup found no one. API-Football's registered club decides whose coach that is; the card's club stands in only when API-Football has no record, and when the two disagree (`isSameClub`) nobody is named.
- **Chat:** `conversationalScout` looks up the clubs in play, passes them to the model as `<verified_managers>`, and gives them to the scrub as `clubManagers`. A turn about the past skips both: it names past coaches only from its evidence.
- **Gates** (`packages/engine/src/gates/managerMentions.ts`): `scrubUnverifiedManagerText` replaces coach names the turn didn't verify. `scrubFormerCoaches` rewrites a club's immediate predecessor to its current coach, only for clubs the text names and never for someone currently coaching another club in play. `strictCurrentCoach` closes the loophole where a sacked coach counts as verified because search text mentions him.
- API-Football's coach is no longer written into grounding text. It's kept only as the lookup's cross-check.

**Critical quirks:**
- `DEFAULT_FAST_MODEL` (`constants/modelProfiles.ts`) picks the model for the whole app pipeline: `gemini-4-hydrogen`, with `gemini-3.8-flash` kept as a profile to switch back to. The Gaffa outlook engine pins its own `FLASH_MODEL` (`packages/engine/src/constants.ts`).
- `gemini-3.8-flash` and `gemini-4-hydrogen` both reject `ThinkingLevel.MINIMAL` (HTTP 400); `aiClient.ts` maps the `minimal` tier to `LOW`. Hydrogen defaults to high thinking, so its profile names low for every task.
- Hydrogen ignores `temperature` (an out-of-range value is a 400), so requests send it only through `samplingFor`, which leaves it out for Hydrogen. A temperature-0 call such as the debate brief isn't deterministic on Hydrogen.
- Thinking tokens count against `maxOutputTokens`. 3.8 Flash reports none at low, but Hydrogen spends up to about 1,800 on a search digest, so every hard cap goes through `outputCap`, which adds the profile's `thinkingHeadroomTokens`; a bare cap returns an empty `MAX_TOKENS` reply on Hydrogen.
- `SIMULATION_YEAR` / `SIMULATION_SEASON` (`prompts/scoutCore.ts`) are computed once at module load from the real date via `getRealWorldFootballSeason`, so the system instruction stays byte-stable within a process for Gemini's implicit prompt caching. Per-turn prompts read the date through `getCurrentSeasonInfo()`.
- The EAFC playstyle directory is only injected when the query matches an EAFC pattern — `buildConversationalScoutInstruction(includeEAFC)` controls this.
- `CALIBRATION_EPOCH_MS` in `dossierCache.ts` marks the last rating recalibration. `isRatedOnCurrentScale` keeps older cards (by their own `createdAt`, falling back to row time) out of the cache, peer ledger, prior-rating memory, the Hub and sharing, so old-scale numbers never anchor a new rating. Cards rated before the 2026-10-20 recalibration were moved to the RLS-locked `player_profiles_pre_recalibration` table. When you change the scale, bump the epoch and archive the same way. The 2026-10-26 rule rewrite (ability-first tiers, peer placement) deliberately kept the epoch: cards are records of when they were rated, so existing cards stay in use as rated and anchor new ones.
- Shared cards: a current card is the one shared card for `CARD_REFRESH_DAYS` (30) from its evaluation date, prime cards are frozen (except a bare "rerate <player>" command: `route.rerate` regenerates the prime card with no prior card, revision or own ledger entry in context, stamps `rerateAt`, and the `20261026120000_prime_rerate` trigger lets the newer `rerateAt` replace the pointer and archive rows; when the new window moves the evaluation date the old archive row stays, and `dropSupersededPrimes` hides it from the Hub, season lookups and prior cards; no prompt mentions it), and accepted challenges stay personal revisions logged to `dossier_revisions` (3 agreeing people re-rate early). The `enforce_dossier_refresh_window` trigger (`supabase/migrations/`) mirrors `CARD_REFRESH_DAYS`, `CALIBRATION_EPOCH_MS` and `REVISION_CONSENSUS_USERS`, so change them in both places. Inside the window only the Latest Update moves: `latestUpdateRefresh.ts` rewrites it from fresh facts (the same live season record and club data as a new current card, plus one news search) once it is `LATEST_UPDATE_REFRESH_DAYS` (7) old, stamps `latestUpdateAsOf`, and writes the pointer row only (same evaluation date, so the trigger allows it).
- Versions, not legacies: a card rates one version of a player (current form, prime, or a named past season), never a career. `classifyTurn` reads a past season from the message (`requestedSeason`) and the pipeline rates that season as a `season_snapshot` card, stored only under its archive slug and found by `getCachedSeasonCard`. With no timeframe, the career status from `getPlayerIdentity` sends a retired player to his prime, and a published prime is served on that answer alone, before any grounding. A prime is a window, not one season: the stretch of consecutive seasons (at most `MAX_PRIME_WINDOW_SEASONS`, 3) when he played at his best, chosen by level rather than output, and rated at the level he sustained across it. The model returns `version.primeWindow`; `sanitizeProfileData` derives `seasonOrEra` ("2003-06") and the label from it, and a longer window fails validation. A multi-season window never answers a single-season request (`seasonMatches`), so that season gets its own season card. Prime cards from before windows keep their one season and still serve as that season's card.
- Eras: a named version of a player ("PSG Neymar", "young Messi", "the Barcelona version of Neymar") is an `era` card. `classifyTurn` reads it from the message (`eraIn`, else the classifier's `requestedEra`), only on dossier requests with no season or current-form cue. The model picks a window like a prime's (at most `MAX_PRIME_WINDOW_SEASONS`, the seasons when he was most fully that version) and `applyVersionRules` stores the user's name for it in `version.qualifier`. An era is defined by its years: the card key and archive slug use the window (`neymar-jr--era--2017-20`), it lives only under that archive slug like a season card, and `findEraCard` answers a request with an era card of the same name (`toEraKey`), or after synthesis with any era, prime or season card covering the same seasons, so the first card published for those years stays the card. An era named after the club he plays for now (API-Football) is his current form unless he has retired. Era cards skip the manager lookup.
- Positions: `CANONICAL_POSITIONS` has no separate Striker (it maps to Centre Forward). `Libero` is for sweeper-era cards only: `resolveLiberoPosition` pairs it with a modern position (`Libero/Centre-Back` by default) and files it under Centre-Back on current cards.

### Welcome walkthrough
`WelcomeWalkthrough.tsx` replaces the old update popup: six steps for a first-time visitor (what Futbolpedia is, reading a rating, Scout, the library, the analyst, Gaffa), shown once (`futbolpedia-welcome-seen-v1`) on a first visit to the chat, never over a shared card or chat, and again from the header's guide button. Its example cards take their ratings and labels from the card index, so they never show a rating the library has changed. Signed out of Gaffa, the composer's Gaffa button explains what Gaffa is and links to its guide and sign-up page.

### Frontend State
`App.tsx` manages all state via React hooks. The header's Dossiers button toggles the main view between **Chat** and **Dossiers** (`view`); the logo also returns to Chat. `DossierHub.tsx` is the one dossier browser: a "Global hub" tab (`fetchGlobalHubDossiers`, first and the default) and a "Your dossiers" tab (the local `futbolpedia-global-dossiers` list, with rename/remove/share), sharing one card grid and filter bar. A search that finds no card offers to Scout that name. Scout's panel shows only recent cards and links to Your dossiers for the rest. The edition filter splits Current, Prime, Eras and Seasons, and each card links to the player's other versions in that tab (current form, prime, eras, seasons) as chips. Era pills are blue, so a named chapter of a career doesn't read as the prime. A card's **Ask** button takes it into the chat: it adds the card to the conversation as a `dossierKey` stub and fills the input with `cardReference` ("Neymar Jr, Paris Saint-Germain era (2017-20): "), whose edition words and season keep the reply on that version. It is layered over the chat so both keep their scroll and state. `SidePanel.tsx` only reads one dossier; it has no list of its own. Opening a global card adds it to your dossiers.

Two persistence layers:
- **`localStorage`** — Conversations (`futbolpedia-conversations`), active dossiers (`futbolpedia-global-dossiers`), theme, active conversation ID
- **Supabase** — `player_profiles` (dossier cache, `player_data` JSONB), `shared_conversations` (share codes), and the shared `club_managers`, `club_snapshots` and `era_snapshots` caches (the two snapshot tables are written only by the server)

On init, `App.tsx` runs a migration path: old `futbolpedia-chat-history` / `futbolpedia-all-profiles` keys are consolidated into the newer `futbolpedia-conversations` schema. A one-time purge (`services/legacyDossiers.ts`, flag `futbolpedia-legacy-purge-v1`) then drops local cards from before the current pipeline, and any card whose player and edition the shared store has never held. Conversation titles are written by Flash from the opening exchange (`services/chatTitle.ts`); a rename sets `titleSource: 'user'` and is never overwritten.

### Key Types (`types.ts`)
- `PlayerProfile` — The central data model. Contains `basicInfo`, `ratings` (overall/potential), `attributes` (25 outfield), optional `goalkeeperAttributes`, `strengths`, `weaknesses`, `playstyleAndRole`, `shortBio`, `latestUpdate`.
- `Conversation` — Wraps an array of `ChatMessage` plus the `activeProfile` and `allProfiles` at the time.
- `ChatMessage.content` is a union: `string | PlayerProfile | ReactNode`.

### Prompt Engineering (`prompts/`, re-exported by `constants.ts`)
- `scoutCore.ts` — shared scouting philosophy, Section III rating tier scale, the 25+7 attribute framework, and named protocols (A–Q: B = injury quarantine, E = stat-lock, M = temporal firewall, Q = contextual triangulation, …). Kept byte-stable as the cached prompt prefix.
- `chatPrompt.ts` — conversational scouting mandate (Section VIII) built by `buildConversationalScoutInstruction`.
- `dossierPrompt.ts` — schema-aligned calibration and synthesis workflow (Section VI).
- **No specific examples in prompts.** Guidance that shapes cards or chat prose must be descriptive: no player names, rating anchors, quoted sample phrases or jargon lists, because the model reuses them. Format specs (YYYY-YY, label templates, enum values) are fine.
- Tier bands, canonical positions, club/position normalization and attribute labels live in `constants/ratingTiers.ts` and must match `types.ts` and the synthesis schema.
